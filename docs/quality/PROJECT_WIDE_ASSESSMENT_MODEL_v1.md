# نموذج تقييم جودة المشروع ككل — الإصدار 1.0

**المالك:** تقييم مشروع Accountant Engine  
**التاريخ:** 2026-11-28  
**الحالة:** نموذج المشروع المستخدم في التقييم المعمق؛ مستقل عن المعيار الرسمي للنواة المحاسبية.  
**النطاق:** المستودع كمنتج كامل، بما يشمل Kernel وSDK والعقود العامة والتخزين والمدارات ووحدات IFRS/IAS والاختبارات والتشغيل والتوثيق.

## 1. الغرض

يحدد هذا النموذج أوزاناً موحدة لتقييم هندسة Accountant Engine ككل. أوزان `ACCOUNTING_KERNEL_QUALITY_STANDARD.md` تبقى خاصة بتقييم النواة، ولا تُنقل تلقائياً إلى المنتج الكامل. هذا النموذج لا يغيّر ذلك المعيار ولا يزعم أنه معيار مؤسسي معتمد.

## 3. مبررات توزيع الوزن

- **39%** للصحة المحاسبية والتخزين والاختبارات؛ لأن خطأ المجال أو فقدان/تكرار الأثر يفسد القيمة الأساسية للمنتج.
- **28%** للمعمارية، القدرات، وSDK؛ لأنها تحدد ما يستطيع المنتج تقديمه فعلياً وما يمكن للمضيف الاعتماد عليه.
- **15%** للأمان والتشغيل؛ لأن العزل والتعافي ضروريان لاستخدام مالي متعدد الشركات.
- **18%** للأداء والصيانة والتوثيق والإصدارات؛ عوامل مهمة لاستدامة المنتج، لكنها لا تعوض فشل الثوابت أو المعاملات.

هذه المجموعات تفسر التوازن العام؛ لا تضف نقاطاً مستقلة ولا تكرر احتساب المحاور.

## 4. طريقة التقدير والحساب

لكل محور درجة من 0 إلى 10، مع تسجيل مصادر الدليل وحدوده:

| الدرجة | التفسير |
| ---: | --- |
| 0–2 | القدرة غائبة أو التنفيذ غير صالح. |
| 3–4 | تنفيذ أولي مع فجوات جوهرية. |
| 5–6 | تنفيذ جزئي؛ توجد مخاطر أو متطلبات مهمة غير مثبتة. |
| 7–8 | جيد مع نواقص محددة وخطة إغلاق واضحة. |
| 9 | قوي وناضج، مع ثغرات محدودة. |
| 10 | مكتمل، قابل لإعادة الإنتاج، ومثبت بأدلة مناسبة للنطاق والبيئة. |

المعادلة:

`Project Score = Σ (Axis Weight × Axis Rating / 10)`

تُحسب الدرجات الوسيطة دون تقريب، ويكون التقريب للعرض إلى منزلة عشرية واحدة. يجب نشر جدول المحاور والأوزان والدرجات والأسباب، لا الرقم الكلي وحده.

### حالات الأدلة

- **Verified:** الدليل يخص commit ونطاقاً وبيئة محددين ويبلغ المستوى المطلوب للمحور.
- **Not Verified:** الدليل غير كافٍ أو يخص commit مختلفاً؛ لا يسمى نجاحاً ولا رسوباً.
- **Failed:** ثبت عدم استيفاء متطلب منطبق؛ ينعكس ذلك في درجة المحور والبوابة ذات الصلة.
- **N/A:** لا يُستبعد محور أو متطلب إلا بسبب نطاق موثق وموافق عليه؛ يعاد تطبيع الأوزان المتبقية.
- **Waived:** استثناء منفصل لا يتحول إلى Pass ولا يخفي القيد. يذكر معه السبب والمالك والمدة والضوابط التعويضية.

إذا تعذر التحقق من محور بسبب اختلاف commit أو غياب البيئة، تعرض الدرجة الرقمية كتقدير مؤقت فقط وتظهر حالة التحقق منفصلة. لا يجوز تقديمها كشهادة اجتياز.

## 5. قواعد عدم ازدواج الاحتساب

1. صحة القيد والتوازن تُحسب في المحور 1؛ أثرها على rollback والتزامن يحسب في المحور 3 من جانب التخزين فقط.
2. وجود اختبار وظيفي يُحسب في محور القدرة عند الحكم على تغطيتها؛ جودة مجموعة الاختبارات وربط الأدلة تُحسب في المحور 7، دون خصم الفجوة نفسها مرتين.
3. وجود API عام يثبت سطح التكامل في المحور 5؛ اتجاه الاعتماد وحدود الطبقات في المحور 2.
4. RLS والعزل الفعلي في المحور 6؛ جودة عقد storage isolation لا تعاد خصمها في المحور 3 إلا إذا كان الخلل متعلقاً بذرية التخزين.
5. أداء النواة أو المحول يقيم في المحور 9، ولا يعوض نتائج محاور المحاسبة أو التخزين.

## 6. بوابات القرار

الدرجة الموزونة لا تعوض فشل متطلب حرج. قرار `GO` للمشروع يتطلب على الأقل:

- ثوابت محاسبية حرجة وعقود تخزين وعزل منطبقة ناجحة بأدلة E3 كحد أدنى.
- عدم وجود متطلب حرج `Not Verified` على commit الإصدار.
- استثناءات `Waived` ظاهرة ومعتمدة، ولا تمس ثابتاً محاسبياً أو عزلاً مطلوباً.
- اختبار كل وحدة Go مستقلة ضمن مسار الإصدار، بما فيها وحدات `go.mod` المتداخلة.
- تحقق E4 للادعاءات التي تعتمد على خصائص بيئة إنتاجية، أو تسجيل Waiver صريح وعدم ادعاء تحقيقها.

تُستخدم بوابات النواة G01–G11 حيث تنطبق، وتضاف بوابات المنتج اللازمة للمدارات والوحدات والتكامل. تجاوز عتبة رقمية وحده لا يمنح `GO`.
