> **قاعدة الحفظ:** المعرفات والمتطلبات والمصطلحات المحاسبية المنقولة من المصدر لا تتغير دون Change Request رسمي.

# مواصفة معمارية الوثائق (Documentation Architecture Specification)

**الحالة:** مواصفة تنظيمية للحزمة v2.0.0.
**الغرض:** تحديد حدود الوثائق ومصادر الحقيقة وروابط الاعتماد وقواعد الإصدار والتحقق، ومنع التكرار والتعارض وفقد المتطلبات أثناء التقسيم.

## 1. المبادئ الحاكمة

1. **Single Source of Truth:** لكل نوع معلومة مالك معياري واحد؛ بقية الوثائق تشير إليه ولا تنسخ نصه إلا عند الحاجة إلى فهرسة صريحة.
2. **Stable Identifiers:** لا يعاد استخدام معرفات ACC / DOM / TXN / MON / LIFE / AUD / ARC / ISO / TEST / PERF / OPS أو G01–G11.
3. **Explicit Dependencies:** كل وثيقة تذكر مرجعها وإصدارها والوثائق التي تعتمد عليها.
4. **Version Consistency:** جميع ملفات الحزمة تحمل إصدار معيار متوافقاً؛ لا تخلط أجزاء من إصدارات مختلفة.
5. **No Silent Semantic Changes:** النقل لا يجيز إعادة الصياغة التي تغير مستوى الإلزام أو النطاق أو معيار القبول.
6. **Traceability:** كل متطلب معياري قابل للتتبع إلى محور درجة وبوابة ودليل واختبار مرجعي عند انطباق ذلك.

- المعيار الأساسي هو المرجع الدلالي الأعلى.
- البوابات ودليل الأدلة تابعان للمعيار ولا يجوز أن يعرّفا متطلبات متعارضة.
- Scope Profile instance يملأ لكل تقييم، ولا يعدّل معيار التصنيفات.
- Test Suite Index يربط المتطلبات بالاختبارات ولا يستبدلها.

## 6. قواعد الروابط والإحالات

- تستخدم روابط Markdown نسبية داخل `docs/quality/`.
- يجب أن تكون كل إحالة إلى ملف موجود، وأن تتطابق أسماء الملفات مع الأسماء المعتمدة.
- عند الإحالة إلى متطلب، استخدم معرفه الثابت لا رقم السطر أو ترتيب الجدول فقط.
- أي نص مقتبس لغرض الفهرسة يجب أن يحدد الوثيقة المالكة له.
- لا تستخدم نسخاً متعارضة من الجدول نفسه في أكثر من وثيقة؛ استخدم رابطاً أو مقتطفاً موسوماً بأنه فهرسة.

## 7. سياسة الإصدارات والتوافق

- رقم إصدار الحزمة يتبع إصدار المعيار المرجعي: `2.0.0`.
- تغيير معنى متطلب أو وزن أو Gate أو Evidence rule يتطلب رفع Major وتحديث جميع الوثائق المتأثرة.
- إضافة متوافقة لمتطلب/اختبار أو توضيح لا يغير المعنى يتطلب Minor وفق قرار المالك.
- تصحيح رابط أو خطأ إملائي لا يغير المعنى يتطلب Patch.
- لا يعتمد إصدار حزمة إذا اختلف رقم الإصدار المرجعي بين الملفات.
- Scope Profile يحمل رقم إصدار القالب الذي أنشئ منه، إضافة إلى رقم إصدار المعيار.

## 8. قواعد منع التكرار والتعارض

1. تعريف الثابت المحاسبي يملكه المعيار؛ فهرس الاختبارات يذكر معرفه ويربطه بالاختبار.
2. شروط Pass/Fail تملكها مواصفة البوابات فقط.
3. تعريف Evidence Level وحساب الدرجات يملكه دليل الأدلة والتقييم فقط.
4. تصنيف القدرة ومعنى N/A يملكه المعيار؛ Scope Profile يسجل قرار الانطباق الخاص بالتقييم.
5. Test Suite Index لا يثبت النجاح بمجرد وجود صف أو اسم اختبار.
6. عند اكتشاف تعارض، يُسجل Issue ويوقف اعتماد الإصدار المتأثر حتى حسمه من Standard Owner.

## 9. التحقق الآلي قبل الإصدار

يجب أن تتحقق CI أو أداة تحقق محلية من الآتي:

- وجود الملفات الستة وREADME.
- عدم وجود روابط Markdown نسبية مكسورة.
- وجود ACC-001 إلى ACC-013 وG01 إلى G11 دون فقد أو إعادة استخدام.
- تطابق إصدار الحزمة في رؤوس الوثائق.
- مجموع أوزان المحاور يساوي 100%.
- تطابق Requirement IDs بين المعيار ومصفوفة التتبع والفهرس.
- عدم وجود ادعاء بأن المشروع اجتاز المعيار لمجرد إنشاء الوثائق.
- وجود حالة لكل اختبار: Not Run / Pass / Fail / Blocked، مع Commit وEnvironment عند تسجيل تشغيل.

## 10. مراحل تنفيذ التقسيم

1. تثبيت المصدر: حفظ نسخة 2.0.0 المرجعية دون تعديل.
2. إنشاء الهيكل: إنشاء الملفات الستة وREADME.
3. النقل: نقل الأقسام إلى وجهاتها وفق جدول التوزيع.
4. الإحالات: إضافة روابط نسبية وبيان المرجع الحاكم لكل ملف.
5. فحص الاكتمال: مقارنة معرفات الثوابت والبوابات والمتطلبات وقوائم التحقق بالمصدر.
6. فحص الدلالة: مراجعة بشرية للتأكد من عدم تغيير الإلزام أو المعنى أو معايير القبول.
7. إصدار الحزمة: تسجيل checksum وملاحظات الإصدار وحالة الاعتماد.

## 11. معايير قبول نجاح التقسيم

- لا يوجد قسم معياري أصلي مفقود من الحزمة.
- كل قسم له مالك واحد واضح.
- جميع روابط Markdown الداخلية صالحة.
- كل معرف ثابت موجود مرة تعريفية واحدة، ويمكن الإشارة إليه في ملفات أخرى.
- جميع شروط G01–G11 مطابقة للمصدر.
- أوزان المحاور ما زالت 100%.
- لا يوجد اختلاف دلالي غير معتمد بين النسخة المفردة والحزمة.
- كل وثيقة تشير إلى إصدار المعيار الصحيح وحالته.
- تم التصريح بأن الحزمة مسودة مرشحة للمراجعة وليست اعتماداً نهائياً.

## 12. الحوكمة والمسؤوليات

- **Standard Owner:** يفسر المعيار ويقود التغيير الدلالي.
- **Documentation Maintainer:** يحافظ على الروابط والبنية والفحوص الآلية.
- **Independent Reviewer:** يراجع اكتمال النقل وعدم تغير المعنى.
- **Approval Authority:** تعتمد الإصدار النهائي وفق RACI في دليل الأدلة والتقييم.

## 13. سجل القرار

تم إنشاء هذه الحزمة من `ACCOUNTING_KERNEL_QUALITY_STANDARD_v2.0.0.md` مع فصل الوثائق حسب المسؤولية. النقل النصي للأقسام الأساسية حافظ على محتوى المصدر؛ أما Scope Profile فهو قالب تعبئة، وCompliance Test Suite Index هو فهرس وربط لا يدعي وجود الاختبارات. يجب إجراء مراجعة مستقلة قبل اعتماد الحزمة رسمياً.
