## 0. تعليمات حاكمة للوكيل

هذه الوثيقة هي خطة تنفيذ وتحقق، وليست إذناً بإعادة تصميم المشروع أو توسيع نطاقه. يجب على المنفذ اتباع القرارات التالية قبل لمس الشيفرة.

### 0.1 حدود التغيير

1. جميع التعديلات البرمجية والاختبارات ووثائق Kernel الجديدة أو المعدلة في هذه المهمة يجب أن تكون داخل `internal/kernal/` فقط.
2. يمنع تعديل أي ملف خارج `internal/kernal/`، بما في ذلك `go.mod` و`go.sum` وملفات CI والسكربتات العامة وSDK وSPI وواجهات API والتخزين والمدارات والوحدات المعيارية.
3. يسمح بتشغيل اختبارات الحزم المحيطة وقراءة عقودها باعتبارها أدلة توافق فقط. لا يسمح بتعديل تلك الحزم ضمن هذه المهمة.
4. إذا كشف الاختبار أن إثبات سلوك معين يتطلب تغييراً في Host Executor أو Storage Adapter، فيجب تسجيل ذلك كاعتماد خارجي في التقرير، وعدم تنفيذ التغيير خارج Kernel.
5. لا تستعد الملفات أو تحذفها آلياً لمجرد اختلافها عن إصدار أقدم. يجب المحافظة على وظائف v11 الصحيحة، وأي إزالة أو تغيير عقد يتطلب قراراً موثقاً واختبار توافق.
6. يجب تسجيل خط الأساس الحالي قبل التعديل: بصمة الأرشيف أو Commit/Tag، وقائمة ملفات `internal/kernal/`، ونتائج الاختبارات المتاحة.

### 0.2 حدود النواة التي يجب الحفاظ عليها

Kernel مسؤول عن قواعد المجال المحاسبي والتحقق والتطبيع والحسابات الدقيقة وتحديد أثر القيود وبناء عقود التنفيذ وسلسلة التدقيق. ولا يدّعي تنفيذ قدرات المضيف.

**داخل النطاق:**

- `types`: المعرفات والعملات والمبالغ والتقريب وأنواع الأخطاء.
- `journal`: نموذج القيد ودورة حياته ونسخه.
- `posting`: التحقق، التطبيع، التوازن، الفترات المستهدفة، العكس، وتسليم Snapshot إلى Executor.
- `masterdata`: قواعد أهلية الشركة والحسابات والدليل واليوميات ومراكز التكلفة والأبعاد والتقويم.
- `policy`: قواعد الترحيل المحاسبية الفعالة زمنياً.
- `valuation`: أسعار الصرف والتحويل وإعادة تقييم البنود النقدية وفق النطاق المحدد للمشروع.
- `governance`: سلسلة التدقيق والتحقق من اللقطة ونقطة التحقق.
- `ledger`: نماذج مرجعية خفيفة فقط وفق `ledger/doc.go`.
- `apperrors`: تصنيف الأخطاء.
- اختبارات Kernel ووثائقه.

**خارج النطاق ويجب ألا يُنقل إلى Kernel:**

- PostgreSQL أو أي تنفيذ تخزين أو SQL أو شبكة.
- أرصدة الأستاذ العام المادية أو Trial Balance أو التقارير المالية أو استعلامات التقارير.
- SDK وAPI وSPI وواجهات المضيف.
- Orbitals والدفاتر الفرعية والمخزون والأصول الثابتة.
- تطبيقات IFRS 9 وIFRS 15 وIFRS 16 وIAS 12 المستقلة.
- المصادقة وRBAC والتفويض والصلاحيات وموافقات المستخدمين وMaker-Checker.
- RLS أو WORM الفعلي أو تنفيذ ACID داخل Kernel.

**ملاحظة مهمة بشأن `ledger`:** يعرّف `internal/kernal/ledger/doc.go` أن `ledger.Account` و`ledger.FiscalPeriod` نماذج مرجعية خفيفة، وأن `masterdata` هو المصدر المرجعي لقواعد الدليل والتقويم. يجب احترام هذا الفصل. لا تُضف Balance Calculator أو Trial Balance أو Balance Sheet أو P&L أو Cash Flow إلى `ledger` ضمن هذه الخطة.

### 0.3 تعريف 10/10

لا تعني 10/10 أن كل سطر Go يجب أن يكون مغطى أو أن Kernel ينفذ وظائف Host. المقصود هو:

- جميع قواعد المجال الـ27 لها تعريف غير ملتبس.
- كل قاعدة لها موضع تنفيذ واضح أو تصنيف صريح `Host Responsibility` أو `Out of Kernel`.
- كل قاعدة داخل Kernel مثبتة باختبارات سلوكية فعلية: قبول ورفض وحدود بحسب طبيعتها.
- لا يوجد خلل P0 أو P1 مفتوح.
- لا يوجد تناقض بين الوثائق والشيفرة والاختبارات وتقرير الإصدار.
- كل حدود المضيف موثقة في العقود، ولا تدّعي النواة ضماناً لا تستطيع تنفيذه.
- نتائج الاختبار والتغطية والأدوات موثقة بمخرجات قابلة للمراجعة.

- `KERNEL_COMPLETION_REPORT.md` ما زال يحمل عنوان وإصدار v10 ويعلن 10/10.
- `KERNEL_TRACEABILITY_MATRIX.md` يحمل عنوان v10 ورمز `AE-TRACE-KERNEL-V10`.
- `KERNEL_RELEASE_BASELINE.md` يحمل خط أساس v10، ويشرح جرداً سابقاً لا يمثل بالضرورة جرد v11 الحالي.

هذه الوثائق يجب تحديثها في إصدار التثبيت، وعدم ترك تقرير v10 باعتباره تقرير v11. كما يجب عدم إبقاء إعلان 10/10 سابقاً دون أدلة تخص الإصدار المراد اعتماده.

## 1.5 ملاحظة عن نطاق الأرشيف

بالمقارنة بين أرشيفي v10 وv11 ظهرت تغييرات خارج `internal/kernal`، بما فيها ملفات جديدة ومعدلة ومحذوفة في مجالات أخرى من المشروع. قد تكون أعمالاً متوازية أو تخص مراحل مختلفة، لكنها تعني أن عبارة «كل التغييرات بين الأرشيفين كانت داخل Kernel» لا تصف المقارنة الكاملة.

لهذه المهمة، يكون معيار Gate Scope هو التغييرات الجديدة من خط أساس v11 إلى الإصدار المستهدف فقط. لا تُعدل الملفات الخارجية الموجودة في الأرشيف، ولا تحذفها، ولا تنسبها إلى هذه المهمة. يجب توثيق Commit/Tag أو بصمة v11 التي يبدأ منها العمل، ثم إثبات أن فرق المهمة الجديدة لا يحتوي ملفات خارج `internal/kernal/`.

2. حدد الحزمة والملف والدالة التي تطبق القاعدة.
3. تحقق أن التنفيذ يفرض القاعدة في المسار الفعلي، لا أن الدالة موجودة فقط.
4. حدد اختبار قبول فعلياً.
5. حدد اختبار رفض فعلياً.
6. حدد اختبار حدود/Fuzz/Property إذا كانت القاعدة حسابية أو معرضة للمدخلات العشوائية.
7. حدد هل يوجد اعتماد على Host Executor.
8. حدد الحالة الحقيقية: `Implemented`, `Partially Implemented`, `Host Responsibility`, أو `Out of Kernel`.
9. لا تضع `Implemented` إذا كان الشرط الحاسم لا يُفرض داخل Kernel.

### 5.3 التحقق الآلي من أسماء الاختبارات

اكتب اختباراً أو أداة تحقق داخل Kernel (ويفضل `doc_test.go` أو اختبار وثائقي) تقوم بـ:

- قراءة أسماء `Test...` و`Fuzz...` من ملفات الاختبارات.
- استخراج الأسماء المذكورة في المصفوفة.
- رفض أي مرجع غير موجود.
- كشف أي صف لا يحتوي اختبار قبول ورفض متى كانت القاعدة تتطلبهما.

يجب ألا تعتمد المطابقة على اسم الاختبار فقط؛ أضف مراجعة بشرية لدلالات Assertions.

### 5.4 فحص دلالي للـAssertions

لكل اختبار مشار إليه، تحقق من:

- أنه يستدعي الدالة أو المسار المستهدف.
- أنه لا يمر فقط بسبب `return nil` أو `t.Skip`.
- أنه يفحص نتيجة القبول/الرفض.
- أنه يتحقق من نوع الخطأ عند أهمية نوع الخطأ.
- أنه لا يبتلع الخطأ أو يتجاهله.
- أنه لا يعتمد على ترتيب اختبار سابق أو حالة مشتركة مخفية.
- أنه يستخدم بيانات واقعية أو حدية مناسبة للقاعدة.

## 7.1 توثيق مراحل الترحيل وترتيبها

17. تمرير Snapshot إلى `PostingExecutor`.

لا تفترض أن الترتيب أعلاه مطابق بالضرورة للتنفيذ الحالي؛ على الوكيل مقارنة كل نقطة بالكود، ثم إما إثبات وجودها أو تصحيح موضعها. يجب أن يسبق أي حفظ أو تنفيذ نهائي كل تحقق محاسبي يمكن للنواة إجراؤه.

## 7.2 Idempotency

Kernel يفرض وجود مفتاح غير فارغ، لكن منع التكرار الحقيقي عبر الطلبات مسؤولية Executor/Host.

يجب أن توثق الواجهة:

- نطاق المفتاح: شركة/عملية/قيد، وفق العقد المعتمد.
- هل يسمح بإعادة إرسال المفتاح نفسه مع Payload نفسها؟ النتيجة يجب أن تكون نتيجة العملية الأصلية دون قيد جديد.
- ماذا يحدث إذا استخدم المفتاح نفسه مع Payload مختلفة؟ يجب إرجاع تعارض صريح.
- كيف يتعامل Executor مع طلبين متزامنين بالمفتاح نفسه؟ يجب أن يثبت Commit واحد فقط.
- كيف يُحفظ المفتاح مع القيد والآثار المحاسبية في وحدة ذرية واحدة؟ Host Responsibility.

لا تدّعِ أن Kernel يمنع التكرار إذا كان يقوم فقط بالتحقق من non-empty key.

## 7.3 Clock وDeterminism

- يجب أن يستخدم `PostEntry` قراءة واحدة من `Clock` في العملية.
- يجب أن تستخدم كل اختبارات التاريخ Clock ثابتاً، لا `time.Now()` الفعلي.
- يجب تثبيت المنطقة الزمنية وسياسة UTC.
- يجب اختبار تغير اليوم/الساعة أثناء تنفيذ الطلب للتأكد أن السياسة وPostedAt يستخدمان اللحظة ذاتها.
- يجب أن تتصرف الدوال `...At` بشكل حتمي للمدخلات نفسها.

## 7.4 Snapshot وعدم تعديل مسودة المستخدم

افحص ما إذا كان التطبيع والتقريب يغيران القيد الممرر بالمرجع.

المطلوب:

- إما العمل على Clone ثم بناء Snapshot منه.
- أو توثيق بوضوح أن `PostEntry` يستهلك/يعدل المسودة، مع اختبارات تثبت ذلك.
- الأفضل ألا تتغير مسودة المستخدم عند فشل التحقق أو فشل Executor.
- لا تسمح بمشاركة slices أو pointers تجعل تعديل Snapshot يغير القيد الأصلي دون قصد.

## 7.5 عقد Executor

وثق أن `PostingExecutor` و`PostingReversalExecutor` مسؤولان عن:

- Atomic commit للقيد والأسطر.
- تخصيص رقم القيد/التسلسل.
- تسجيل Idempotency Key.
- تحديث/حفظ الأرصدة إن كانت ضمن نموذج التخزين لدى المضيف.
- حفظ سجل التدقيق وربطه بالقيد.
- قفل/تسلسل عكس القيد الأصلي.
- rollback كامل عند أي فشل.

Kernel يضمن التحقق وبناء Snapshot؛ لا يضمن ACID أو RLS أو SQL بنفسه.

## شروط القبول

- لا يوجد مسار Posting يتجاوز أي invariant.
- جميع حالات فشل التبعيات تعيد أخطاء محددة لا Panic.
- لا تغير المسودة عند فشل العملية، إلا إذا كان العقد يصرح بخلاف ذلك.
- Clock واحد في العملية.
- كل آثار التسوية تظهر في Snapshot.
- عقد Executor يفرق بوضوح بين ضمان Kernel وضمان Host.

| الفترة المستهدفة | Regular | Adjusting عادي | Closing | Audit Adjusting | Opening | Reversing |
| --- | --- | --- | --- | --- | --- | --- |

- رقم الفترة لا يُستخدم بديلاً عن هوية السنة/الفترة.
- الفترة الإضافية تتبع نفس FiscalYear والشركة.
- Audit type لا يمر في الفترات العادية.
- أنواع Adjusting العادية لا تمر في الفترة 14.
- لا يُقبل نوع Audit إذا كانت الفترة 14 غير موجودة أو مغلقة.

## 8.3 Reversal

يجب إثبات جميع العلاقات:

- الأصل موجود ومرحّل.
- القيد العكسي Draft قبل الترحيل.
- `ReversalOfID` يشير إلى الأصل الصحيح.
- `ReversedByID` في الأصل لا يتعارض مع قيد عكسي آخر.
- `ReversalReason` غير فارغ.
- تاريخ العكس لا يسبق تاريخ الأصل.
- فترة العكس تحل حسب تاريخ العكس، لا تاريخ الأصل.
- الحسابات والأبعاد والعملات تحفظ وفق قواعد العكس.
- المدين والدائن يتبادلان.
- صافي الأثر لكل حساب بعد الأصل والعكس يساوي صفراً، في حدود دقة MinorUnit والسياسة المعتمدة.
- عمليتا عكس متزامنتان لا تنشئان إلا عكساً واحداً بعد التزام Executor بالعقد الذري.

## 8.4 ملخص ما قبل الإقفال

تأكد أن `SummarizeAdjustingEntriesForPreClose`:

- يلتقط نقص البيانات.
- يلتقط نوع Adjusting غير المعروف.
- يلتقط Audit خارج 14.
- يلتقط Adjusting عادي داخل 14.
- يلتقط سبباً فارغاً.
- يميز بين القيود المرشحة والمخالفة.
- يقدم Evidence قابلة للمراجعة، مع ID القيد وسبب رفضه.

- لا يمكن بناء/ترحيل عكس بلا سبب.

# 11. المرحلة السابعة: Audit Chain وSnapshot وCheckpoint

## 11.1 Hashing

## 11.2 Atomic Append Contract

`AtomicAuditLogRepository` مسؤول عن:

1. تخصيص SequenceNumber.
2. قراءة PreviousLogHash الصحيح ضمن نفس التسلسل الذري.
3. تثبيت Timestamp.
4. حساب CurrentLogHash بعد اكتمال الحقول.
5. حفظ السجل كوحدة ذرية.
6. منع سجلين للشركة نفسها من أخذ التسلسل نفسه.

Kernel يعرّف العقد ويتحقق من الناتج؛ لا ينفذ قاعدة بيانات أو قفل موزع.

## 11.3 Consistent Snapshot Verification

- يجب الحصول على Logs وCheckpoint وSnapshotSequence من لقطة متسقة واحدة.

- إعادة المحاولة محدودة وواضحة.
- نفاد المحاولات ينتج `RetryableConsistencyError` منفصلاً عن خطأ العبث.
- إذا كانت اللقطة نفسها مستقرة لكن الهاش أو التسلسل غير صحيح، فهذا `IntegrityViolation` وليس Retry.
- تحقق من CompanyID في كل سجل وفي Checkpoint.
- تحقق من البداية Genesis، والترتيب، والتسلسل، والهاش السابق، والهاش الحالي، وحد اللقطة، وآخر Hash.

```bash
go test -shuffle=on -count=20 ./internal/kernal/...
```

## 15.6 Coverage

```bash
go test -covermode=atomic -coverprofile=/tmp/kernel-v12.cover ./internal/kernal/...
go tool cover -func=/tmp/kernel-v12.cover
```

ثم احسب التغطية لكل حزمة حرجة على حدة، ولا تكتف بالنسبة الإجمالية.

## 15.7 Fuzz

شغل كل هدف على حدة بمدة مناسبة، مثال:

```bash
go test ./internal/kernal/types -run=^$ -fuzz=FuzzMoneyFromStringNeverPanics -fuzztime=2m
go test ./internal/kernal/types -run=^$ -fuzz=FuzzMoneyJSONNeverPanics -fuzztime=2m
go test ./internal/kernal/masterdata -run=^$ -fuzz=FuzzGenerateFiscalYearMaintainsContinuityAndContainment -fuzztime=2m
go test ./internal/kernal/posting -run=^$ -fuzz=FuzzValidateEntryDoubleEntryNeverPanics -fuzztime=2m
go test ./internal/kernal/posting -run=^$ -fuzz=FuzzEntryLineRejectsCurrencyAndExchangeRateMismatch -fuzztime=2m
go test ./internal/kernal/posting -run=^$ -fuzz=FuzzBalancedEntryProperties -fuzztime=2m
go test ./internal/kernal/posting -run=^$ -fuzz=FuzzRoundingResidualRequiresExplicitSettlement -fuzztime=2m
go test ./internal/kernal/posting -run=^$ -fuzz=FuzzReversalNetImpactIsZeroPerAccount -fuzztime=2m
go test ./internal/kernal/governance -run=^$ -fuzz=FuzzAuditSnapshotDetectsPayloadTampering -fuzztime=2m
```

إذا تغيرت أسماء أهداف Fuzz، يجب تحديث الأوامر والمصفوفة، وعدم إبقاء أوامر تشير إلى أهداف غير موجودة.

## 15.8 اختبار النقاء المعماري

```bash
go test ./internal/kernal -run TestKernelArchitectureUsesPureInterfaces -count=1
```

## 15.9 أدلة التشغيل الواجب حفظها

- نسخة Go الفعلية.
- Command line الكامل.
- Exit code.
- stdout/stderr عند الفشل.
