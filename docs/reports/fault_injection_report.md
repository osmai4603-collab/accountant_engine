## 1. الغرض والمنهج

يحاكي حقن الأعطال انقطاعاً عند كل نقطة من حدود وحدة العمل: قبل حجز المفتاح، قبل التدقيق، قبل ظهور الكتابات، وبعد أن تصبح دائمة وقبل وصول الاستجابة. الحاقن محايد عن المحول ويُمرَّر عبر `context` بـ `storage.WithFaultInjector`؛ شيفرة الإنتاج الطبيعية لا تمرره، ولا توجد أعطال دائمة في قاعدة الشيفرة.

القاعدة المختبرة: **الفشل قبل Commit يعني صفر أثر، والفشل بعد Commit يعني نتيجة محفوظة قابلة للاسترجاع**.

## 2. نقاط الحقن

| النقطة | الموضع الدلالي | التنفيذ في الذاكرة | التنفيذ في PostgreSQL | النتيجة المتوقعة |
|---|---|---|---|---|
| `FaultBeforeIdempotencyClaim` | قبل إنشاء/حجز السجل الدائم | قبل قفل المحول ونسخ اللقطة | قبل فتح المعاملة في `CommitPosting` | لا مفتاح، لا قيد، لا أثر |
| `FaultBeforeAudit` | بعد تجهيز القيد والأثر وقبل تدقيق إلزامي | داخل القسم الحرج قبل `appendAuditInternal` | داخل UoW قبل `AppendAudit` | Rollback كامل؛ لا حركة بلا تدقيق |
| `FaultBeforeCommit` | بعد تجهيز كل الكتابات وقبل جعلها مرئية | قبل استبدال لقطة المحول | قبل `tx.Commit()` | لا قيد ولا مفتاح ولا رصيد ولا تغيير في الأصل المعكوس |
| `FaultAfterCommit` | بعد الالتزام وقبل إرجاع القيد للمتصل | بعد استبدال اللقطة | بعد إغلاق المعاملة بنجاح | خطأ unknown outcome؛ الاستعلام بالمفتاح يُرجع النتيجة |

## 3. سيناريوهات الاختبار

### 3.1 الفشل قبل Commit

يُحقن الخطأ في كل نقطة من النقاط الثلاث الأولى بمفتاح جديد، ثم تُفحص أربع حقائق:

1. `GetEntry` لا يجد القيد.
2. `Lookup` لا يجد سجل idempotency.
3. رصيد النقدية يبقى `0`.
4. في العكس: الأصل يبقى `posted` و`ReversedByID == nil`.

هذا يمنع النمط الخطير «قيد محفوظ بلا تدقيق» أو «أصل معكوس بلا عكس».

### 3.2 الفشل بعد Commit

يُحقن `FaultAfterCommit` أثناء أول طلب. يُعاد خطأ للمتصل رغم أن الالتزام نجح. ثم:

1. `Lookup(companyID, key)` يُرجع `completed` مع `EntryID`.
2. إعادة الطلب بنفس المفتاح والبصمة تُعيد نفس `EntryID`.
3. الرصيد النهائي `100` وليس `200`.

هذا هو بروتوكول unknown outcome؛ لا تخمين ولا إنشاء قيد بديل.

## 4. نتائج التنفيذ

| السيناريو | Memory | PostgreSQL | ملاحظة |
|---|---|---|---|
| `IdempotentReplayAndPayloadConflict` | PASS | PASS | replay بلا كتابة، وتعارض صريح بالبصمة |
| `KernelStampedDates` | PASS | PASS | طوابع النواة محفوظة كما هي |
| `FaultInjectionAtomicity` | PASS | PASS | النقاط الأربع مغطاة؛ قبل Commit بلا أثر وبعده قابل للاسترجاع |
| `ReversalAtomicity` | PASS | PASS | rollback لا يغيّر الأصل؛ العكس الثاني مرفوض |
| `ConcurrentReplay` | PASS | PASS | فائز واحد وأثر واحد |
| `CompanyScopeIsolation` | PASS | PASS | لا تسرب بين الشركات |

الأرقام المحدثة والمدد لكل حالة في [تقرير التكافؤ المولّد](contract_parity_report.md) وفي `test/contract_parity/parity_report.md`. هذه الملفات مولّدة آلياً؛ تشغيل حزمة فرعية يعيد كتابتها بعدد السيناريوهات المشغّلة فقط، لذا يُعتمد تشغيل المستودع كاملاً عند إغلاق الفجوات.

## 5. ملاحظات خاصة بكل Adapter

- **Memory:** التحقق من السباق وال回滚 يتم بقفل الوحدة ونسخة لقطة قبل أي تعديل؛ `FaultAfterCommit` يُختبر بعد تثبيت اللقطة الجديدة. لا يدّعي المحول متانة قرصية.
- **PostgreSQL:** `FaultBeforeCommit` يُلقى داخل معاملة واحدة تضم `Claim` و`PostEntry` و`AppendAudit` واكتمال idempotency؛ أي خطأ يُلغي الالتزام. قفل الأصل `FOR UPDATE` يمنع فائزين متزامنين في العكس.
- كلا المحولين يُرجعان نفس sentinels المحايدة؛ لا تظهر رموز SQL أو تفاصيل السائق في نتائج الاختبار.

## 6. الحدود

- لا يختبر هذا التقرير أداءً أو SLO؛ قياسات الأداء خارج نطاق المرحلة 7.
- `FaultAfterCommit` يحاكي فقدان الاستجابة داخل العملية، لا انقطاع شبكة فعلي؛ الاستنتاج المنطقي هو نفسه لأن الحالة الدائمة قابلة للاستعلام.
- القفل المادي وترتيب الأقفال تحت التزامن العدائي المكثف متروكان للمرحلة 8؛ هذه المرحلة تثبت فائزاً واحداً على مستوى العقد لا سياسة Deadlock كاملة (`G-002`).

## 7. الحكم

جميع نقاط الحدود الأربع مغطاة بمجموعة العقد المحايدة على المحولين. لا يوجد مسار يُثبت نجاحاً جزئياً، ولا حركة مالية بلا أثر تدقيقي، ولا نتيجة فقدان استجابة بلا استعلام آمن. تفاصيل القرارات والقيود في [`KERNEL_REMEDIATION_PHASE7_REPORT.md`](../KERNEL_REMEDIATION_PHASE7_REPORT.md).
