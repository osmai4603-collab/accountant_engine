**اسم الخطة:** Kernel Final Hardening & 100% Scope Completion  
**رمز الوثيقة:** `AE-PLAN-KERNEL-FINAL-010`  
**الإصدار المستهدف:** الإصدار العاشر وما بعده حتى بوابة الاعتماد النهائي  
**خط الأساس الذي تمت مراجعته:** `accountant_engine9.zip`  
**تاريخ إعداد الخطة:** 2026-11-21  
**الحالة:** خطة تنفيذ مقترحة — لا تعني أن المهام قد نُفذت أو اجتازت الاختبارات  
**النطاق البرمجي الملزم:** `internal/kernal/` فقط

## 0. الغرض من الوثيقة وطريقة استخدامها

هذه الوثيقة ليست قائمة أفكار عامة، وليست دعوة لإعادة تصميم المشروع. إنها خطة إغلاق تنفيذية للنواة المحاسبية الحالية، مبنية على فحص الإصدار التاسع ومقارنته بالإصدار الثامن، وعلى مراجعة وثائق المشروع المتاحة داخل الأرشيف، وعلى القرارات المعمارية التي حُسمت في المحادثة.

الغرض هو الوصول إلى نواة محاسبية مكتملة **ضمن المسؤوليات المعتمدة لها**، بحيث تكون كل قاعدة:

1. محددة بعبارة غير ملتبسة.
2. مرتبطة بموضع تنفيذ واضح داخل `internal/kernal`.
3. مرتبطة باختبار يثبت القبول والرفض والحالات الحدية.
4. متوافقة مع عقود النواة والأنظمة المضيفة.
5. موثقة بنتيجة تنفيذ فعلية، لا بمجرد وجود ملف اختبار.

### 0.1 قاعدة أساسية

**لا تعتبر أي وظيفة مكتملة لمجرد وجود struct أو method أو interface أو test باسم مناسب.** الاكتمال يتطلب تحقق السلوك المطلوب، واتصال التنفيذ بمسار العمل الصحيح، ووجود اختبار يثبت ذلك.

### 0.2 معنى 100% في هذه الخطة

تعني 100% اكتمال المتطلبات المعتمدة داخل نطاق Kernel، ولا تعني:

- تغطية أسطر برمجية 100% بالضرورة.
- خلو البرنامج من كل عيب ممكن رياضياً.
- اعتماداً محاسبياً أو قانونياً خارجياً.
- إثبات ذرية قاعدة بيانات لا تنفذها النواة أصلاً.
- اكتمال النظام المحاسبي بكامل وحداته المدارية.

لا يصح إعلان 10/10 إلا بعد اجتياز بوابة القبول في القسم 15، مع الإفصاح عن الاعتمادات التي تقع خارج Kernel.

# 1. القرارات المعمارية الثابتة وحدود التنفيذ

هذه القرارات ملزمة لجميع مراحل الخطة. لا يجوز للوكيل تغييرها من تلقاء نفسه.

## 1.1 حصر التعديلات البرمجية داخل Kernel

يسمح بتعديل أو إضافة أو حذف الملفات داخل:

```text
internal/kernal/
```

ولا يسمح بإجراء تعديلات برمجية أو توثيقية أو إعدادات بناء خارج هذا المجلد ضمن هذه المهمة، بما في ذلك:

```text
pkg/
storage/
internal/orbitals/
internal/events/
internal/reconciliation/
modules/
test/                 # خارج internal/kernal
scripts/
docs/                 # جذر المشروع
go.mod
 go.sum
 CI / workflows
```

يسمح للوكيل بقراءة الملفات الخارجية وفحص العقود وتشغيل اختبارات الحزم المرتبطة كأدلة توافق فقط، بشرط عدم تعديلها.

إذا اكتشف الوكيل أن إثبات تكامل معين يتطلب تغييراً خارج `internal/kernal`، فعليه:

1. توثيق الاعتماد الخارجي.
2. توضيح لماذا لا يمكن إثباته من داخل Kernel وحده.
3. إضافة اختبار عقد داخلي أو fake/mock يثبت جانب Kernel الممكن.
4. تسجيله كعنصر اعتماد خارجي في التقرير النهائي.
5. عدم تنفيذ التعديل الخارجي.

## 1.2 ما هو مستبعد صراحة

لا تضف ولا تُعد تسمية ولا تُدخل بصورة غير مباشرة أياً من التالي:

- RBAC.
- الأدوار والصلاحيات والتفويض.
- المصادقة وإدارة المستخدمين والجلسات.
- Maker-Checker أو موافقات المستخدمين.
- موافقات Workflow.
- HTTP أو REST أو gRPC أو طبقة نقل.
- SQL أو PostgreSQL أو محولات التخزين.
- SDK أو API أو خدمات التطبيق.
- تقارير القوائم المالية أو الدفاتر الفرعية أو الخزينة أو المطابقة أو التوحيد.
- وحدات IFRS/IAS الاختيارية.

تبقى الحقول `ActorID` و`CreatedBy` و`PostedBy` و`Reason` بيانات إسناد وتدقيق فقط. لا يجوز استخدامها لإثبات صلاحية أو تفويض.

## 1.3 حدود مسؤولية Kernel والمضيف

| المسؤولية | Kernel | المضيف / Executor |
|---|---|---|
| صحة القيد المزدوج | ينفذ ويفرض التحقق | لا يعيد تفسير القاعدة |
| تطبيع المبالغ والتقريب | ينفذ ويصدر قيداً مطبعاً | يحفظ المخرجات كما استلمها |
| أهلية الحساب واليومية والفترة | يتحقق من البيانات والسياسات المقدمة عبر المنافذ | يوفر بيانات متسقة وحديثة |
| إنشاء القيد العكسي | ينشئ Draft ويحدد بيانات العكس | يربط الأصل بالعكس ذرياً ويمنع العكس المكرر |
| قرار الترحيل المحاسبي | يمر عبر `PostingPipeline` | لا يتجاوز Kernel في تدفق الترحيل المعتمد |
| ذرية الحفظ وقفل قاعدة البيانات | يحدد عقد المنفذ ومتطلبات النتيجة | ينفذ المعاملة والقفل والتثبيت والتراجع |
| Idempotency validation | يفرض وجود المفتاح ويحدد عقده | ينفذ replay/conflict ذرياً ويحفظ النتيجة السابقة |
| سجل التدقيق | يبني الهاش ويتحقق من السلسلة واللقطة | يوفر append ذرياً ونقطة تحقق خارجية موثوقة |
| المصادقة والتفويض | خارج النواة | مسؤولية المضيف |

**تنبيه اعتماد:** نجاح Kernel لا يثبت وحده أن PostgreSQL أو Executor يحقق ACID أو RLS أو منع التكرار أو حفظ نقطة التحقق خارجياً. هذه اعتمادات مضيف، وتُذكر منفصلة في شهادة الاكتمال.

## 1.4 لا تغيّر المعمارية قبل إثبات الحاجة

المبدأ هو إصلاح النواة الحالية وتثبيت عقودها. أي إعادة تسمية واسعة، أو نقل حزم، أو تغيير API عام، أو إزالة ملف يُستخدم خارج Kernel يتطلب قراراً معمارياً موثقاً واختبارات توافق. لا تُجر تغييرات واسعة لمجرد تحسين الشكل.

# 2. مصادر الحقيقة وترتيب الأولوية

تم إعداد الخطة بالاستناد إلى هذه المصادر الموجودة في الأرشيف:

1. الإصدار التاسع: الشيفرة الفعلية داخل `internal/kernal`.
2. الإصدار الثامن: وثيقة `internal/kernal/KERNEL_ACCOUNTING_INVARIANTS.md` التي لم تظهر في الإصدار التاسع، إضافة إلى اختبارات سابقة حُذفت أو لم تعد موجودة.
3. `docs/TARGET_ACCOUNTING_KERNAL.md`: يحدد حدود Kernel والفصل عن Orbitals وStorage وSDK.
4. `docs/ACCOUNTING_BUSINESS_RULES.md`: قواعد المحاسبة العامة، مع ضرورة التمييز بين القواعد الواقعة داخل Kernel والقواعد الخاصة بالمكونات المدارية.
5. `docs/ENGINEERING_BUSINESS_RULES.md`: المتطلبات الهندسية، خصوصاً العزل المعماري والتحديدية والذرية ومفتاح عدم التكرار.
6. `docs/ACCOUNTING_ENGINE_ACCEPTANCE_CRITERIA.md` و`docs/ACCOUNTING_ENGINE_SUCCESS_CRITERIA.md`: شروط المشروع العامة، وتُستخدم مرجعاً للقراءة لا للتعديل في هذه المهمة.

### 2.1 ترتيب فض التعارض

إذا ظهر اختلاف بين مصدرين:

1. لا تُخفِ التعارض ولا تُصلحه بصمت.
2. حدد القاعدة والوثيقتين المختلفتين.
3. قدم قراراً مقترحاً مع أثره المحاسبي والتوافقي.
4. استخدم هذا القرار في التنفيذ فقط إذا كان منسجماً مع حدود Kernel والقرارات الثابتة أعلاه.
5. سجّل التغيير في وثيقة القرار داخل `internal/kernal/`.

### 2.2 قواعد ليست من Kernel

القواعد المتعلقة بالدفاتر الفرعية AR/AP، والخزينة، والمطابقة البنكية، والتقارير، ومعادلة القوائم، والتوحيد، والمعايير المتخصصة لا تُنقل إلى Kernel لمجرد وجودها في `ACCOUNTING_BUSINESS_RULES.md`. وثيقة `TARGET_ACCOUNTING_KERNAL.md` تصنف هذه الوظائف ضمن Orbitals أو Modules اختيارية.

يمكن لـ Kernel توفير بيانات ونتائج محاسبية موثوقة تستهلكها تلك المكونات، لكنه لا يصبح محرك تقارير أو دفتر عملاء أو موردين ضمن هذه الخطة.

# 4. قرارات يجب تثبيتها قبل التنفيذ

هذه قرارات مقترحة لتجنب اجتهاد الوكيل في أمور تؤثر على عقد النواة.

## DEC-01 — حدود التغيير

**القرار:** جميع تغييرات الشيفرة والاختبارات والوثائق الجديدة داخل `internal/kernal` فقط. الاختبارات خارج Kernel يمكن تشغيلها للقراءة والتحقق دون تعديلها.

## DEC-02 — Audit Snapshot

**القرار:** اعتماد `Consistent Snapshot Verification`.

- تؤخذ سجلات الشركة ونقطة التحقق من لقطة منطقية واحدة.
- اللقطة تحمل `CompanyID` و`SnapshotSequence` و`Checkpoint.Version` و`Checkpoint.SequenceNumber` و`Checkpoint.LogHash`.
- التقدم المتزامن بعد التقاط اللقطة لا يجعل اللقطة القديمة فاسدة؛ التحقق الحالي ينتهي عند حد اللقطة.
- إذا اكتشف المستودع أن السجلات أو حدها أو نقطة التحقق تغيرت أثناء إنشاء اللقطة، يعيد `ErrAuditSnapshotConflict`.
- تعارض الالتقاط قابل لإعادة المحاولة بعدد محدود (القيمة الحالية 3 محاولات ما لم يثبت الاختبار ضرورة تغييرها).
- استمرار التعارض ينتج `ErrAuditSnapshotConsistencyRetryable`، وليس `ErrAuditChainBroken`.
- اختلاف الهاش أو التسلسل داخل لقطة ثابتة يعد مخالفة سلامة، ولا يعالج بإعادة المحاولة لإخفائه.

**قرار إضافي:** النموذج الحالي يفرض أن `SnapshotSequence` يساوي تسلسل نقطة التحقق، وأن اللقطة تحتوي كامل السجلات من 1 حتى ذلك التسلسل. لا تسمح بالتقليم أو حذف بادئة السلسلة إلا إذا أضيف Anchor/Genesis offset موثق واختبارات تثبته. لا تخفف هذا الشرط بصمت.

## DEC-03 — دقة Money

**القرار المقترح:** اعتماد 28 رقماً ذا دلالة و12 منزلة عشرية كحد للمقياس الداخلي، اتساقاً مع `InternalScale = 12` ومع قاعدة الإصدار الثامن `RULE-KERNEL-005`.

لكن اختبار v9 يقبل `1.1234567890123` (13 منزلة). لذلك يجب على الوكيل إظهار هذا التعارض في تقرير التنفيذ. التوصية هي الالتزام بعقد 12 منزلة، وتعديل الاختبار ليختبر الرفض أو التقريب الصريح. إذا قرر مالك المنتج دعم 13 منزلة فأكثر، فيجب تعديل قاعدة الدقة رسمياً داخل وثيقة Kernel واعتماد سقف تمثيل صريح قبل التنفيذ.

ويجب وضع حد للأس الكبير/عدد المنازل ولعدد الأرقام في الجزء الصحيح أيضاً؛ لأن حصر أرقام المعامل وحده لا يمنع قيماً مثل `1e999999` من إنتاج تمثيل JSON ضخم.

## DEC-04 — قيمة AdjustingEntryAudit

**القرار المقترح:** المحافظة على القيمة النصية السابقة `audit_adjustment` بدلاً من `audit`، لأنها جزء من عقد بيانات محتمل وقد تكون مستخدمة في بيانات أو تكاملات سابقة. إذا كانت هناك ضرورة لتغييرها، يلزم دعم قراءة القيمتين وخطة انتقال واضحة؛ ولا يُنفذ التغيير بصمت.

## DEC-05 — حدود حزمة `ledger`

وثيقة `TARGET_ACCOUNTING_KERNAL.md` تحدد سبع حزم مركزية ولا تسمي `ledger` ضمنها، بينما الحزمة موجودة في الشيفرة ويستخدمها سطح API الخارجي كأنواع مرجعية. كما أن دفتر الأستاذ والتقارير تظهر في المشروع ضمن المكونات المدارية.

**القرار المقترح لهذه الخطة:**

- لا تنشئ داخل Kernel محرك تقارير أو Trial Balance أو Balance Sheet أو AR/AP أو Treasury.
- لا تضف طبقة تخزين أو تحديث أرصدة.
- حافظ على أنواع `ledger` الحالية المتوافقة مع المستهلكين.
- وثّق داخل `internal/kernal/ledger/doc.go` حدود الحزمة وعلاقتها بـ `masterdata`، وحدد ما إذا كانت الأنواع مجرد Domain Contracts أو قيمة مستقلة.
- لا تحذف الحزمة ولا تغير حقولها العامة دون تحليل أثر التوافق.
- إذا تقرر لاحقاً أن حساب حركة الأستاذ/الرصيد التراكمي مسؤولية Kernel، يلزم قرار معماري منفصل يحدد القواعد والحدود أولاً. هذا التوسع ليس مفترضاً في الخطة الحالية.

## DEC-06 — نوع إعادة التقييم

لا توجد في وثيقة الثوابت السابقة قاعدة تلزم بإضافة `AdjustingEntryRevaluation`. لذلك لا تضف هذا النوع تلقائياً. افحص معنى الأنواع الحالية وما إذا كانت إعادة التقييم تصنف Accrual وفق سياسة العمل المعتمدة. وثّق القرار، ثم أضف نوعاً مستقلاً فقط إذا وافق مالك القواعد المحاسبية على ذلك.

# 5. مراحل التنفيذ التفصيلية

## المرحلة 0 — تجميد خط الأساس وحماية النطاق

**الأولوية:** P0  
**الهدف:** منع تكرار مشكلة الإصدار التاسع التي أصلحت جزءاً وأزالت أجزاء أخرى أو عدلت ملفات خارج النطاق.

### الملفات داخل النطاق

- `internal/kernal/doc.go`
- ملفات `doc.go` الخاصة بكل حزمة.
- أي ملف جديد داخل `internal/kernal/` عند الحاجة.

### خطوات التنفيذ

1. أنشئ جرداً لكل ملفات Kernel الحالية، مع تصنيفها إلى Source وTests وDocs وTestdata.
2. أنشئ قائمة مقارنة مع الإصدار الثامن داخل تقرير الخطة أو ملف `KERNEL_RELEASE_BASELINE.md` داخل Kernel.
3. سجل الملفات التي اختفت من v8، ولا تستعدها قبل تصنيف محتواها.
4. افحص جميع imports داخل Kernel وتأكد من أنها لا تستورد `pkg/` أو `storage/` أو `orbitals/` أو SQL أو HTTP أو شبكات.
5. افحص حقول البيانات العامة والأنواع النصية التي قد تكون عقوداً متبادلة.
6. أنشئ قاعدة مراجعة تمنع أي مهمة لاحقة من حذف اختبار قائم دون بديل يثبت السلوك نفسه.
7. لا تعدّل `go.mod` أو `go.sum`؛ إصدار Go المطلوب مثبت في المشروع.

### السبب

الإصدار التاسع يُظهر أن التقدم الوظيفي يمكن أن يترافق مع تراجع في وظائف سابقة. لذلك يجب بناء خط أساس يمنع الانحدار (Regression) قبل إضافة إصلاحات.

### اختبارات القبول

- تقرير الجرد يطابق ملفات `internal/kernal` الفعلية.
- لا توجد Imports محظورة داخل Kernel.
- لا يوجد ملف خارج Kernel معدّل ضمن مهمة الإكمال.
- لا يُحذف اختبار دون ربطه باختبار بديل في مصفوفة التتبع.

### شرط الإغلاق

اعتماد قائمة الملفات والاختبارات الحالية كخط أساس، مع توثيق جميع الاختلافات عن v8.

## المرحلة 1 — استعادة وثيقة الثوابت ومصفوفة التتبع

**الأولوية:** P0  
**الهدف:** جعل كل قاعدة محاسبية قابلة للتتبع من المتطلب إلى الشيفرة إلى الاختبار.

- `internal/kernal/doc.go` (تحديث الحدود عند الحاجة)
- ملفات `doc.go` للحزم التي تتطلب توضيحاً.

### خطوات التنفيذ

1. استعد وثيقة `KERNEL_ACCOUNTING_INVARIANTS.md` من الإصدار الثامن كأساس، لا كنسخة نهائية عمياء.
2. احتفظ بالقواعد `RULE-KERNEL-001` إلى `RULE-KERNEL-027`، وراجع كل نص مقابل الكود الحالي.
3. أضف حالة كل قاعدة: `Implemented`, `Partially Implemented`, `Missing`, `Host Responsibility`, `Out of Kernel`.
4. أنشئ صفاً لكل قاعدة يتضمن:
   - `Rule ID`.
   - نص المتطلب.
   - الحزمة والملف.
   - الدالة المسؤولة.
   - اختبار قبول.
   - اختبار رفض.
   - الحالات الحدية/التزامن عند اللزوم.
   - هل يوجد اعتماد على Host Executor؟
   - نتيجة التنفيذ الفعلية.
5. ميّز بين ثوابت Kernel وبين قواعد المشروع العامة ACC-028 وما بعدها التي تنتمي إلى Orbitals/Reporting/Subledgers/Standards حسب المعمارية.
6. اربط قواعد التدقيق `RULE-ACC-041` إلى `RULE-ACC-043` بقواعد الحوكمة داخل Kernel عندما ينطبق ذلك، دون توسيع النطاق إلى تقارير أو وحدات معايير.
7. لا تكتب أن القاعدة مكتملة قبل وجود تنفيذ واختبار ناجح.

### السبب

غياب وثيقة الثوابت من v9 يقطع سلسلة التتبع. كما أن قواعد العمل العامة تشمل وظائف ليست من مسؤولية Kernel، لذلك يجب أن تمنع المصفوفة توسيع النواة بالخطأ.

### شرط الإغلاق

- كل قاعدة Kernel لها مالك برمجي واختبار محدد.
- لا توجد حالة `Unknown` أو قاعدة بلا تفسير.
- كل قاعدة ذات مسؤولية مضيف موثقة بهذه الصفة بدلاً من ادعاء تنفيذها داخل Kernel.

## المرحلة 2 — إصلاح التقويم المالي Fiscal Calendar

**الأولوية:** P0  
**الهدف:** استعادة تاريخ بداية السنة المخصص وضمان أن الفترات كاملة ومتتابعة دون فجوات أو تداخل.

### الملفات

- `internal/kernal/masterdata/fiscal_calendar.go`
- `internal/kernal/masterdata/fiscal_calendar_test.go`
- `internal/kernal/masterdata/fiscal_calendar_fuzz_test.go` (إنشاء/استعادة)
- `internal/kernal/ledger/period.go` (اختبار اتساق فقط؛ لا تغيّر عقده دون قرار)

### المشكلة المثبتة في v9

`GenerateFiscalYear` يحول البداية إلى أول الشهر:

```go
start = time.Date(start.UTC().Year(), start.UTC().Month(), 1, 0, 0, 0, 0, time.UTC)
```

وبذلك يفقد يوم البداية الذي يرسله المستدعي. الإصدار الثامن كان يحتوي دالة `addFiscalMonths` واختبار `TestGenerateFiscalYearPreservesCustomStartDay`.

### خطوات التنفيذ

1. احذف التطبيع الذي يفرض اليوم الأول من الشهر.
2. طبّع المنطقة الزمنية إلى UTC مع المحافظة على التاريخ التقويمي المقصود.
3. استعد أو أعد بناء `addFiscalMonths(start, n)` بحيث تحسب كل حد انطلاقاً من تاريخ البداية الأصلي، لا من الحد السابق، لتجنب انجراف يوم الشهر.
4. إذا كان اليوم الأصلي غير موجود في الشهر المستهدف، استخدم آخر يوم صالح في ذلك الشهر، وفق سلوك موثق.
5. احسب:
   - `FiscalYear.StartDate` من البداية المطلوبة.
   - `FiscalYear.EndDate` من حد بعد 12 شهراً ناقص وحدة الزمن المعتمدة.
   - بداية كل فترة من `addFiscalMonths(start, i-1)`.
   - نهاية كل فترة من الحد التالي ناقص nanosecond، أو اعتماد تمثيل نصف مفتوح `[start,end)` في حال كان هذا قراراً عاماً جديداً؛ لا تخلط الأسلوبين.
6. احتفظ بالفترتين 13 و14 كفترتين إجرائيتين في نهاية السنة، ولا تجعلهما قابلتين للاختيار عبر `Contains(date)`.
7. تحقق من أن 13 و14 لهما `FiscalYearID` و`CompanyID` نفسيهما للسنة، وأنهما تقعان تماماً على نهاية السنة حسب العقد الحالي.
8. أضف Validator عاماً لتقويم سنة مالية مولّد:
   - 12 فترة عادية بالترتيب 1–12.
   - جميع الفترات داخل حدود السنة.
   - كل فترة تبدأ بعد نهاية السابقة مباشرة وفق دقة الزمن المعتمدة.
   - لا يوجد تداخل.
   - لا توجد فجوة.
   - الفترة 13 نوعها `YearEndAdjustment`.
   - الفترة 14 نوعها `AuditAdjustment`.
   - `Contains` تعيد false للفترتين الإضافيتين.
9. افصل التحقق من صلاحية بيانات الفترة المسترجعة عن التحقق من التاريخ، ولا تثق بقيم Repository دون تحقق دفاعي.
10. احتفظ بسلوك `SoftClosed` وفق `PostingPolicy.AllowSoftClosedPosting`؛ لا تضف موافقات أو صلاحيات.

### مصفوفة الاختبارات الإلزامية

| الحالة | المتوقع |
|---|---|
| بداية 1 يناير | 12 فترة متصلة كما هو متوقع |
| بداية 15 مارس | تبقى البداية 15 مارس |
| بداية 31 يناير | لا تنزاح حدود الأشهر بصورة تراكمية |
| فبراير سنة كبيسة | حد صحيح في فبراير |
| فبراير سنة غير كبيسة | حد صحيح في فبراير |
| بداية 30/31 من شهر | clamp مضبوط في الأشهر القصيرة |
| تاريخ قبل بداية السنة | يرفض |
| تاريخ بعد نهاية السنة | يرفض |
| تاريخ نهاية فترة عادية | يطابق الفترة حسب سياسة الحدود |
| `Contains` للفترة 13/14 | false دائماً |
| فترة فيها فجوة/تداخل | Validator يرفض |
| فترة لا تنتمي للسنة | Validator يرفض |

### Fuzzing

أعد/أنشئ `FuzzGenerateFiscalYearHasContiguousPeriods` بمدخلات تواريخ متنوعة. لا يكتفي الاختبار بمنع التداخل؛ يجب أن يثبت عدم وجود فجوة أو تداخل وأن الفترات جميعها داخل السنة.

### شرط الإغلاق

نجاح اختبارات تواريخ البداية المخصصة وحدود الأشهر والسنة الكبيسة وFuzz دون فجوات أو تداخل.

## المرحلة 3 — إعادة الحتمية الزمنية Clock & Determinism

**الأولوية:** P0  
**الهدف:** أن ينتج عن نفس المدخلات والوقت المثبت نفس القرار ونفس الطوابع الزمنية.

### الملفات

- `internal/kernal/posting/pipeline.go`
- `internal/kernal/posting/entry_validation.go`
- `internal/kernal/posting/reversal.go`
- `internal/kernal/valuation/revaluation.go`
- `internal/kernal/governance/audit_chain.go`
- ملفات الاختبارات ذات الصلة.

### المشكلة المثبتة

في v9 يستخدم `PostEntry` `time.Now().UTC()` عند فحص السياسة، ثم يستدعيه مرة أخرى لتحديد `PostingDate` و`PostedAt`. كما تستخدم دوال إنشاء القيد والعكس وإعادة التقييم وAppend الوقت مباشرة.

### خطوات التنفيذ

1. استعد واجهة `Clock` البسيطة التي توفر `Now() time.Time`، مع System Clock افتراضية.
2. أعد `WithClock(clock)` كخيار لتهيئة `PostingPipeline`، مع تجاهل nil أو استبداله بسلوك موثق.
3. التقط `now := clock.Now().UTC()` مرة واحدة لكل استدعاء `PostEntry`.
4. مرر اللحظة نفسها إلى:
   - `ValidatePostingPolicy`.
   - `PostingDate`.
   - `PostedAt`.
   - أي حقل زمني مشتق من لحظة الترحيل.
5. استعد `NewJournalEntryAt(..., now)`، واجعل `NewJournalEntry` Wrapper يستدعيه بساعة النظام.
6. استعد `BuildReversalEntryAt(..., now)`، واجعل النسخة العادية Wrapper.
7. استعد `GenerateRevaluationEntryAt(..., now)`، واجعل النسخة العادية Wrapper.
8. أضف مساراً قابلاً للاختبار لوقت سجل التدقيق، مثل `AppendAt` أو Clock option داخل governance. لا تجعل governance تستورد posting؛ استخدم واجهة صغيرة محلية أو دالة صريحة لتجنب دورة التبعيات.
9. راجع `ValidateCanPostToAccount` الذي يستخدم الوقت الحالي كـ convenience wrapper؛ يجب أن يستعمل مسار الترحيل الدالة `ValidateCanPostToAccountAsOf` بوقت العملية المحقون، لا Wrapper الوقت الحالي.
10. استهدف منع `time.Now()` في القرارات التجارية. يجوز وجوده داخل System Clock الافتراضية وWrappers العامة فقط.
11. وثق دلالة الوقت: `EffectiveDate` تاريخ الحدث المحاسبي، و`PostingDate` وقت الترحيل الفعلي، ولا تستبدل أحدهما بالآخر.

### الاختبارات

- ساعة ثابتة واحدة تنتج `PostingDate == PostedAt`.
- السياسة ووقت الترحيل يستخدمان اللحظة نفسها.
- وقت قبل/بعد حد Backdating ينتج قراراً حتمياً.
- بناء القيد والعكس وإعادة التقييم بوقت صريح ينتج نفس timestamps كل مرة.
- لا يوجد اختلاف nanoseconds بسبب استدعاء الساعة مرتين.
- اختبارات UTC وحدود اليوم والتاريخ.

### شرط الإغلاق

جميع القرارات الزمنية في عمليات Kernel قابلة للتحديد بحقن الوقت، ولا توجد قراءة وقت غير مضبوطة داخل نفس العملية.

## المرحلة 4 — تثبيت عقد Money & Precision

**الأولوية:** P0  
**الهدف:** منع فقدان القيمة، ومنع قبول أعداد ذات تمثيل غير محدود، وجعل العرض والتخزين والحساب واضحين.

### الملفات

- `internal/kernal/types/money.go`
- `internal/kernal/types/currency.go`
- `internal/kernal/types/rounding.go`
- `internal/kernal/types/errors.go`
- `internal/kernal/types/money_test.go`
- `internal/kernal/types/money_fuzz_test.go`
- `internal/kernal/types/rounding_test.go`

### المشاكل / التعارضات

- `precisionDigits` في v9 يقيس أرقام المعامل بعد إزالة الأصفار النهائية، ولا يحدد عدد المنازل العشرية أو عدد الأرقام الصحيحة.
- اختبار v9 يقبل 13 منزلة عشرية، بينما وثيقة الثوابت في v8 نصت على 12 منزلة كحد داخلي.
- قيم الأس السالبة الكبيرة قد تجعل JSON ينتج تمثيلاً ضخماً؛ والأس الموجب الكبير قد ينتج عدداً صحيحاً هائلاً رغم قلة الأرقام ذات الدلالة.
- `String()` يعرض أربع منازل عشرية؛ يجب عدم الخلط بين العرض المقروء والتمثيل الدقيق.
- `RoundForPosting()` يعيد قيمة fallback عند فشل `Rounded()` بدلاً من إظهار الخطأ، وهو سلوك يحتاج عقداً واضحاً.

### خطوات التنفيذ

1. اعتمد constants مسماة بوضوح، على الأقل:
   - `InternalScale`.
   - `MaximumSignificantDigits`.
   - `MaximumRepresentationalScale`.
   - `MaximumIntegerDigits` أو حد مكافئ يمنع التمثيل غير المحدود.
2. اتبع قرار DEC-03، أو وثق تعديل القرار قبل كتابة الكود.
3. اجعل التحقق من الدقة يحدث في `NewMoney` و`NewMoneyFromString` و`UnmarshalJSON` من خلال مسار واحد.
4. افحص exponent قبل أي `StringFixed` أو `MarshalJSON` لتجنب تخصيص ذاكرة ضخمة.
5. ارفض `NaN` و`Infinity` والقيم غير العددية كما هو قائم، وأضف حالات exponent شديدة الكبر/الصغر.
6. حافظ على رفض `XXX` والعملات غير المعروفة.
7. أضف `ExactString()` أو اسماً مماثلاً يعيد تمثيلاً دقيقاً ضمن الحدود المعتمدة.
8. وثق أن `String()` دالة عرض فقط إذا ظلت مقربة إلى `FinancialScale`، ولا تستخدمها في مقارنة أو Hash أو Persistence.
9. لا تغير توقيع دالة عامة مثل `RoundForPosting()` بصورة تكسر المستهلكين دون بديل متوافق. إن احتاج المسار إلى error-returning API، أضف دالة strict جديدة واستعملها داخل Kernel، ثم وثق deprecation إن لزم.
10. راجع `CurrencyMinorUnit`؛ لا ينبغي أن يبدو رقم `FinancialScale` كأنه MinorUnit صالح لعملة غير معروفة. أضف مساراً يعيد خطأ أو نتيجة صريحة دون كسر API القديم إلا بقرار توافق.
11. تحقق من حدود `int64` عند تحويل minor units، ومن القيم الكبيرة قبل التحويل.
12. تحقق أن JSON Round-trip لا يغير القيمة، ولا يحول قيمة غير صالحة إلى قيمة صالحة بصمت.
13. لا تستخدم `float32` أو `float64` في أي تمثيل أو حساب مالي.

### جدول الاختبارات

| المجال | حالات مطلوبة |
|---|---|
| Sign | موجب، سالب، صفر (وفق عقد Money العام) |
| Significant digits | الحد الأقصى، الحد + 1 |
| Scale | 0، 2، 3، 12، 13، قيمة ضخمة |
| Integer magnitude | الحد، الحد + 1، exponent موجب ضخم |
| Currency | USD، JPY، KWD، YER، XXX، ZZZ |
| Round | Half-even أسفل/عند/أعلى المنتصف |
| Minor units | Exact وSub-minor-unit وOverflow |
| JSON | round-trip، null، invalid JSON، exponent attack |
| Arithmetic | Add/Subtract/Multiply/Divide وحدود overflow |

### Fuzzing / Properties

- أي قيمة يقبلها Constructor يجب ألا تسبب Panic في `String`, `ExactString`, `Rounded`, `MinorUnits`, `RoundingDifference`, `MarshalJSON`.
- أي Money صالح بعد JSON round-trip يجب أن يكون `Equal` للأصل.
- لا يجوز أن تنجح `MinorUnitsExact` إذا كان هناك كسر أصغر من الوحدة النقدية.
- جميع عمليات `Add` و`Subtract` يجب أن ترفض اختلاف العملة.

### شرط الإغلاق

عقد الدقة مكتوب ومطبق ومختبر؛ لا يمكن إنتاج JSON غير محدود؛ ولا يوجد فقدان قيمة صامت.

## المرحلة 5 — إحكام Posting Pipeline وعقد Idempotency

### الملفات

- `internal/kernal/posting/rounding.go`
- `internal/kernal/posting/lock_manager.go`

- `internal/kernal/posting/rounding_precision_test.go`
- اختبارات جديدة داخل `internal/kernal/posting/`.

### خطوات التنفيذ

1. اجعل الترتيب موثقاً وثابتاً:
   1. فحص هوية رأس القيد والأسطر.
   2. فحص التصنيف والبيانات التابعة له.
   3. فحص الحالة Draft.

   5. نسخ القيد بـ `Clone()` قبل التطبيع.

   10. حل الفترة وتطبيق قواعد 13/14/Opening/Closing.
   11. تطبيع مبلغ المعاملة ثم إعادة حساب الوظيفي والتسوية الصريحة.
   12. التحقق النهائي من القيد المزدوج بعد التطبيع.
   13. تحميل الحسابات والتحقق من الملكية والصلاحية والأهلية والأبعاد.
   14. تطبيق سياسة الترحيل.

2. أضف خطأ صريحاً مثل `ErrIdempotencyKeyRequired` إذا لم يوجد، وافرض `strings.TrimSpace(opts.IdempotencyKey) != ""` وفق `RULE-ENG-008`. التحقق من وجود المفتاح داخل Kernel؛ تنفيذ replay/conflict وحجز المفتاح ذرياً مسؤولية Executor/host.
3. وثق بوضوح أن Kernel لا يستطيع وحده إرجاع نتيجة سابقة للمفتاح، لأنه لا يملك مخزن الحالة. لا تدّع تنفيذ Idempotency الكاملة داخل النواة.
4. احتفظ بفصل `PostingExecutor` و`PostingReversalExecutor`. لا تمرر reversal إلى executor الاعتيادي.
5. تأكد من أن عدم توفر `PolicyEngine` أو `Reader` أو Executor المطلوب ينتج خطأ واضحاً ولا يؤدي إلى Panic.
6. تأكد من أن `PostEntry` لا يعدل المسودة الأصلية التي قدمها المستدعي؛ اعمل على Clone، وأعد النسخة المطبعة/المرحلة فقط.

9. تحقق من كل سطر، بما فيه سطر Rounding Settlement المضاف، من ملكية الحساب وأهليته ومتطلبات أبعاده.
10. افحص أن العملة الوظيفية المتماثلة مع عملة المعاملة تفرض ExchangeRate = 1.

13. أضف عقد نتيجة `PostingSnapshot` فقط إذا كان ضرورياً لتمرير بيانات ثابتة/مطبعة للمنفذ؛ لا تضف نوعاً جديداً لمجرد التسمية، ولا تكسر توقيعاً عاماً مستخدماً خارج النواة دون قرار توافق.

## المرحلة 9 — تحصين Governance وAudit Snapshot

**الأولوية:** P1  
**الهدف:** ضمان كشف تغيير السجل أو فقد التسلسل داخل البيانات المتاحة، وربطها بنقطة تحقق خارجية ضمن لقطة متسقة.

### Append Contract

وثق أن `AppendAuditLogAtomic` مسؤول عن:

1. حجز التسلسل التالي للشركة بصورة ذرية.
2. جلب/تثبيت الهاش السابق بصورة ذرية.
3. تثبيت الطابع الزمني وبيانات السجل.
4. حساب `CurrentLogHash` بعد تثبيت SequenceNumber وPreviousLogHash وكل الحقول الداخلة في الهاش.
5. إضافة السجل دون تحديث أو حذف سجلات سابقة.
6. تحديث/ربط نقطة التحقق وفق سياسة checkpoint المعتمدة.
7. منع عمليتي Append متزامنتين من استعمال SequenceNumber أو PreviousHash نفسه.

يجب تحديد هل `AuditLog.ID` معرف تخزيني مستبعد من الهاش، وتوثيق ذلك. جميع الحقول الدلالية يجب أن تدخل في الهاش، بما فيها Reason وPayload وTimestamp وCompanyID وActorID وCorrelationID وAction وEntity metadata وSequenceNumber وPreviousLogHash.

### Snapshot Contract

1. `GetAuditVerificationSnapshot` يعيد `CompanyID` المطلوب نفسه.
2. Logs وCheckpoint من لقطة منطقية واحدة.
3. Logs مرتبة تصاعدياً ولا يوجد تكرار أو فجوة.
4. كل سجل CompanyID يساوي الشركة المطلوبة.
5. `SnapshotSequence` يساوي الحد الذي تقف عنده اللقطة وفق DEC-02.
6. تحقق من `Checkpoint.CompanyID` وVersion وSequenceNumber وHash.
7. تحقق من جميع الهاشات من Genesis حتى الحد.
8. تحقق أن الهاش النهائي يساوي `Checkpoint.LogHash`.
9. إذا تغيرت حدود القراءة أثناء أخذ اللقطة، يرجع المستودع ErrAuditSnapshotConflict.
10. إعادة المحاولة bounded فقط لأخطاء snapshot acquisition/conflict، ولا تعاد محاولة خطأ tampering لإخفائه.
11. `ctx.Err()` يجب أن يوقف المحاولة.
12. إذا انتهت المحاولات، أرجع retryable consistency error.
13. إذا كانت السلسلة مقتطعة من البداية، لا تقبلها دون Anchor موقّع/موثوق وعقد صريح.
14. لا تدّع أن hash chain وحدها تكشف حذف الذيل دون checkpoint مستقل.
15. `NewAuditChain(nil)` أو `AuditChain` غير مهيأة يجب ألا تسبب Panic؛ أعد خطأ dependency واضحاً.
16. اجعل الطابع الزمني قابلاً للاختبار عبر `AppendAt` أو clock option.

### اختبارات التدقيق

### مجموعة اختبارات الخصائص المطلوبة

- Money: constructor/JSON/minor unit/arithmetic invariants.
- Entry: balanced vs unbalanced, line uniqueness, identity, side exclusivity.
- Rounding: conservation of total value and explicit residual settlement.
- Reversal: per-account net impact zero; dimensions preserved.
- Fiscal: contiguous periods, no overlap/gap, custom start day.
- FX: inverse consistency within defined precision; same-currency rate 1; no future rates.
- Audit: hash determinism and snapshot sequence consistency.
- Master data: no cyclic hierarchy and no cross-company ownership.

# 8. العقود التي يجب أن تبقى مسؤولية المضيف

هذه البنود يجب توثيقها داخل Kernel، واختبار جانبها بواسطة fakes، لكن لا تدّع أن Kernel ينفذها بنفسه.

## 8.1 Atomic Posting

`PostingExecutor` يجب أن يلتزم بعقد:

- إما حفظ كامل آثار العملية أو عدم حفظ أي منها.
- عدم تحديث أرصدة مستقلة عن حفظ القيد.
- عدم إكمال العملية إذا فشل Audit Append.
- عدم تثبيت Idempotency Key دون النتيجة المقابلة.
- إرجاع النتيجة المخزنة عند replay مطابق وفق ENG-009.
- رفض استخدام المفتاح نفسه لحمولة مختلفة وفق ENG-010.

Kernel يفرض وجود المفتاح ويعطي بيانات القيد المطبعة؛ المضيف مسؤول عن حفظ المفتاح والنتيجة بشكل ذري.

## 8.2 Atomic Reversal

`PostingReversalExecutor` يجب أن:

- يقفل/يتحقق من الأصل.
- يرفض إذا كان `ReversedByID` موجوداً.
- يحفظ قيد العكس.
- يربط الأصل بالعكس.
- يحدث الحالة التوثيقية للأصل حسب العقد.
- يحفظ الأثر المحاسبي والتدقيق في نفس المعاملة.
- يمنع سباق عكسين متزامنين.

## 8.3 Atomic Audit Append and Checkpoint

المستودع مسؤول عن sequence وprevious hash وcurrent hash والتحديث المتسق لنقطة التحقق. Kernel يتحقق من snapshot ويرفض التضارب أو التلاعب وفق الأخطاء المحددة.

# 12. بوابة الإصدار النهائي Release Gate

لا يعتبر الإصدار مكتملًا إلا إذا تحققت جميع المجموعات التالية.

## 12.1 Gate A — النطاق

- [ ] كل التغييرات tracked داخل `internal/kernal/` فقط.
- [ ] لا تعديل `go.mod` أو `go.sum` أو CI أو Storage أو SDK أو Orbitals.
- [ ] لا RBAC أو Authorization أو Maker-Checker أو Approval workflow.
- [ ] لا import محظور من Kernel.

## 12.2 Gate B — الثوابت

- [ ] كل قواعد `RULE-KERNEL-001..027` موثقة.
- [ ] كل قاعدة مرتبطة بملف/دالة/اختبارات.
- [ ] لا توجد قواعد ذات حالة مجهولة.
- [ ] مسؤوليات المضيف مميزة بوضوح عن مسؤوليات Kernel.
- [ ] جميع قواعد الفترات 13/14 مثبتة في الاتجاهين.
- [ ] القيود العكسية والبيانات التابعة مكتملة.

## 12.3 Gate C — الدقة المالية

- [ ] عقد Precision واحد ومتوافق في الكود والوثيقة والاختبارات.
- [ ] لا `float32` أو `float64` في المال.
- [ ] لا فقدان صامت لوحدة نقدية.
- [ ] لا JSON غير محدود الحجم بسبب exponent.
- [ ] كل أسعار الصرف موجبة ونافذة ومطابقة للزوج والنوع.
- [ ] نفس العملة تعني سعر 1.

## 12.4 Gate D — الترحيل

- [ ] `PostEntry` يرفض كل حالات عدم الاكتمال.
- [ ] لا Executor عند الفشل.
- [ ] Executor يستقبل قيداً مطبعاً ومتوازناً.
- [ ] IdempotencyKey إلزامي في Kernel وفق العقد المعتمد.
- [ ] عكس القيد يستخدم Executor خاصاً.
- [ ] Host atomicity موثقة كاعتماد لا كإنجاز Kernel.

## 12.5 Gate E — Master Data / Fiscal

- [ ] صلاحية الحسابات واليوميات مؤرخة.
- [ ] COA بلا دورات أو آباء غير صالحة حسب عقد الإدخال.
- [ ] الأبعاد ومراكز التكلفة صالحة ومملوكة للشركة.
- [ ] السنة المالية تحفظ يوم البداية.
- [ ] الفترات متصلة بلا فجوات أو تداخل.
- [ ] حالات Open/SoftClosed/HardClosed صحيحة.

# 13. شكل تقرير التسليم الذي يجب أن يقدمه الوكيل

يجب أن ينتهي التنفيذ بتقرير داخل `internal/kernal/KERNEL_COMPLETION_REPORT.md` يحتوي على:

1. **ملخص التغيير:** ماذا تغير ولماذا.
2. **قائمة الملفات:** كل ملف جديد/معدل/محذوف وسبب ذلك.
3. **Traceability:** حالة كل Rule من 001 إلى 027.
4. **Regression report:** كيف تم التعامل مع كل ملف/اختبار كان موجوداً في v8 ولم يظهر في v9.
5. **Test evidence:** الأمر المنفذ، إصدار Go، النتيجة، عدد الاختبارات، ووقت التنفيذ إن توفر.
6. **Coverage:** النسبة الكلية ولكل حزمة حرجة.
7. **Race/Fuzz/Mutation:** النتائج الفعلية، لا التقديرية.
8. **External dependencies:** كل ما يظل مسؤولية Executor أو Storage أو Host.
9. **Known limitations:** أي شيء لم ينفذ أو لم يمكن إثباته.
10. **Release decision:** Pass/Fail مع أسباب واضحة.

يحظر استخدام عبارات مثل "100% مكتمل" أو "جميع الاختبارات ناجحة" إذا لم تكن هناك نتائج تشغيل فعلية محفوظة أو قابلة للمراجعة.

## ملحق ب — تعريف حالات المهام

استخدم الحالات التالية في تقرير التنفيذ:

- `NOT_STARTED`: لم يبدأ العمل.
- `IN_PROGRESS`: يجري التنفيذ.
- `IMPLEMENTED`: تغير الكود، لكن الاختبار لم يثبت بعد.
