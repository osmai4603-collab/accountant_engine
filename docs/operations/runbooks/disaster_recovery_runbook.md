# Runbook: استعادة الكوارث والتحقق من السلامة المحاسبية

- **المعرّف:** RB-OPS-001 / `P7-03` → `T7`
- **الجمهور:** مهندسو العمليات والموثوقية ومسؤولو قواعد البيانات
- **النطاق:** النواة المدمجة (`pkg/sdk`) مع PostgreSQL فقط؛ لا يوجد في هذا المشروع خادم HTTP أو gRPC ولا منفذ `/readyz`.
- **المراجع:** [تقرير التحقق النهائي](../../reports/KERNEL_FINAL_VERIFICATION_REPORT.md)، [اعتماد الإصدار](../../reports/KERNEL_RELEASE_SIGNOFF.md)، [عقد مستودع التدقيق](../../contracts/KERNEL_AUDIT_REPOSITORY_CONTRACT.md).

## 1. شروط ما قبل البدء

1. نسخة معتمدة من `pg_dump --format=custom` أو نقطة PITR مع سلسلة WAL كاملة.
2. قاعدة هدف جديدة فارغة ومعزولة؛ لا تُكتب أبداً فوق قاعدة المصدر.
3. إيقاف كتابة التطبيق المضيف على المصدر المعزول وتسجيل وقت الحادث وإصدار الموديول المستخدم.
4. توفر `pg_dump` و`pg_restore` متوافقين مع إصدار الخادم، وضبط `POSTGRES_URL` أو المقبس المحلي `/var/run/postgresql`.
5. مالك حادث معتمد يملك قرار `GO/NO-GO` بعد الفحوص.

## 2. الاستعادة المعزولة

```bash
# 1) نسخة منطقية من المصدر (قبل العزل أو من أحدث نسخة معتمدة)
pg_dump --format=custom --file="$BACKUP_FILE" "$SOURCE_DSN"

# 2) استعادة إلى قاعدة هدف نظيفة
createdb "$TARGET_DB"
pg_restore --exit-on-error --no-owner --no-privileges \
  --dbname="$TARGET_DSN" "$BACKUP_FILE"
```

بعد الاستعادة لا تُطبَّق هجرات إضافية؛ سجل `schema_migrations` يجب أن يكون مكتملاً ومطابقاً لبصمات الإصدار المستهدف. أي حاجة لإعادة تشغيل الهجرات تعني استعادة غير صالحة.

## 3. الفحوص الإلزامية قبل استئناف الكتابة

تُنفَّذ آلياً بواسطة `go test -v ./test/dr` (المسار `test/dr/dr_drill_test.go`) بالتسلسل التالي:

| # | الفحص | الشرط |
| :---: | :--- | :--- |
| 01 | `pg_dump` | ملف نسخة غير فارغ |
| 02 | `pg_restore` | خروج 0، بلا أخطاء |
| 03 | `ValidateSchema` | سجل هجرات مكتمل، بصمات مطابقة، لا إعادة ترحيل |
| 04 | توازن القيد المزدوج | $\sum \text{debit} = \sum \text{credit}$ لكل قيد ولكل شركة |
| 05 | مطابقة الأرصدة | `driver.AssertBalancesMatchMoves` لكل شركة/فترة/عملة |
| 06 | سلسلة التدقيق | `governance.VerifyAuditIntegrity` لكل شركة ضمن النطاق |
| 07 | عزل RLS | دور فاحص يرى شركة واحدة فقط، ولا صفوف بلا سياق شركة |
| 08 | مفاتيح Idempotency | عدم تكرار الحركة عند إعادة الإرسال |
| 09 | استئناف النشر | ترحيل قيد صالح بعد الاستعادة |
| 10 | عكس ذري | Idempotent reversal ناجح |
| 11 | إقفال سنوي | إقفال ذري مع قيد افتتاح للسنة التالية |

- **RPO المستهدف:** 0 (آخر معاملة ملتزمة قبل النسخة/نقطة PITR).
- **RTO المستهدف:** < 5 ثوانٍ داخل التمرين الآلي؛ يُسجَّل الزمن الفعلي في `docs/reports/p7_gate_evidence.md`.

## 4. قرار الاستئناف

1. ارفض الاستئناف إذا فشل أي فحص من 01–11، أو تعذّر تفسير سجل هجرات، أو ظهر أي تسريب بين الشركات.
2. أرفق في سجل الحادث: مصدر النسخة، لحظة الاستعادة، إصداري PostgreSQL والتطبيق، نتائج الفحوص، RPO/RTO الفعليين، واسم مالك القرار.
3. بعد الاعتماد فقط، وجّه `POSTGRES_URL` في التطبيق المضيف إلى القاعدة المستعادة، وافتح الكتابة تدريجياً مع مراقبة السجلات والتسويات.

## 5. ملاحظات تنفيذية

- `storage/memory` مخصص للتطوير والاختبار ولا يصلح هدفاً للاستعادة.
- التمرين الآلي يفحص النطاق الذي ينشئه بنفسه؛ تقارير `P7-04` يجب أن توضّح ما إذا كان نطاق الإنتاج الكامل قد فُحص أم لا.
- لا توجد نقطة نهاية صحية أو مكون شبكي داخل النواة؛ جاهزية التطبيق المضيف خارجة عن نطاق هذا الدليل.
