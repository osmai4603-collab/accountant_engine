# وثيقة حدود المسؤوليات والملكية والعقود للنواة المحاسبية

## 1. الغرض وطبيعة الوثيقة

تحدد هذه الوثيقة **حدود المسؤوليات والملكية والعقود** للحزم الموجودة داخل `internal/kernal` فقط. وهي مرجع للإجابة عن: **من يملك المفهوم أو القاعدة أو العقد؟ ما الذي يدخل في مسؤوليته وما الذي لا يملكه؟ وما حدود استهلاك الحزم الأخرى لهذه المسؤولية؟**

هذه الوثيقة ليست خريطة طريق، ولا خطة عمل أو ترتيب مراحل، ولا مواصفة تفصيلية لقواعد المجال أو الجودة أو التشغيل. وهي لا تحدد مهاماً أو تواريخ أو أولويات تنفيذية. وظيفتها تثبيت الملكية والحدود ومنع ازدواج مصدر الحقيقة أو انتقال مسؤولية قاعدة من مالكها دون قرار صريح.

**النطاق المحدد:** الحزم `types` و`apperrors` و`journal` و`masterdata` و`policy` و`posting` و`ledger` و`governance` و`valuation` داخل `internal/kernal`.

لا تشمل هذه الوثيقة بقية محرك `accounting_engine`، ولا `Public API` أو `SPI` أو `Application Layer` أو المحولات أو التخزين أو النقل أو الأنظمة المضيفة. يجوز ذكر هذه المكونات فقط لتوضيح حدّ تفويض أو اعتماد، ولا تُعرّف الوثيقة مسؤولياتها أو مواصفاتها.

هذه وثيقة حدود ومسؤوليات؛ لا تصف الملفات أو الدوال أو جداول قاعدة البيانات أو تفاصيل التنفيذ. تفاصيل القاعدة وشروطها وحالاتها الحدية موضعها مواصفات المجال؛ وطرق قياس الالتزام وأدلة الاختبار موضعها مواصفات الجودة؛ وآليات التشغيل والمعاملات والأقفال والتخزين موضعها مواصفات التشغيل والتنفيذ. كما أنها ليست خطة إعادة هيكلة، ولا مواصفة محاسبية بديلة عن IFRS أو المعايير المحلية، ولا إثباتاً بأن كل قاعدة مطبقة حالياً.

**المعنيون:** مالك معمارية حزم `internal/kernal`، ومطورو هذه الحزم، ومراجعو جودة حدودها وعقود التفاعل بينها.

## 2. الأساس المنهجي والمراجع الرسمية

أُعدت الوثيقة بالاستفادة من المراجع التالية، مع تكييفها على طبيعة النواة:

1. **ISO/IEC/IEEE 42010:2022 — Architecture Description.** يحدد متطلبات هيكل وتعبير الوصف المعماري، ويميز بين المعمارية والوثيقة التي تصفها. يهتم بتحديد النظام وأصحاب المصلحة واهتماماتهم ووجهات النظر والعلاقات. لا يفرض قالباً واحداً ولا طريقة تنفيذ بعينها.
2. **Microsoft Learn — Domain Analysis / Bounded Contexts.** يوضح أن لكل سياق محدود نموذجاً مجالياً وحدوداً، وأن النموذج الواحد لا يلزم أن يكون صالحاً لكل المسؤوليات؛ كما يوصي بتوثيق نقاط التفاعل والعقود.
3. **Microsoft Learn — Tactical DDD.** يوضح دور الكيانات والقيم والتجميعات، وأن Aggregate يحدد حد الاتساق، ويفصل خدمات المجال عن خدمات التطبيق التي تنسق حالات الاستخدام.
4. **IFRS Foundation — Conceptual Framework for Financial Reporting.** يوفر الإطار المفاهيمي لعناصر التقارير المالية والاعتراف وإلغاء الاعتراف والقياس والعرض والإفصاح. يُستخدم لفهم حدود المفاهيم المحاسبية، ولا يغني عن المعيار التفصيلي المختص.

هذه الوثيقة ليست شهادة مطابقة لأي مرجع أعلاه، ولا تنسب إلى تلك المراجع أسماء الحزم أو تقسيم المشروع.

## 3. الحالة المعمارية الحالية ونطاق الحزم

بحسب بنية المشروع المرفق، يقتصر نطاق هذه الوثيقة على الحزم التسع الموجودة مباشرة داخل `internal/kernal`:

| الحزمة | المسؤولية المعمارية الموصوفة |
| --- | --- |
| `types` | القيم المالية والأنواع الأساسية |
| `apperrors` | شكل الأخطاء المرمّزة والتوافق مع المستهلكين؛ حزمة معزولة لا تستهلكها حالياً بقية حزم النواة |
| `journal` | القيد المحاسبي ودورة حياته |
| `masterdata` | البيانات المرجعية المحاسبية |
| `policy` | السياسات والأهلية |
| `posting` | التحقق والترحيل والعكس |
| `ledger` | إسقاطات القراءة الحتمية ونماذج التوافق المرجعية؛ لا يملك الحقيقة المرجعية للحسابات أو الفترات |
| `governance` | التدقيق وسلامة الأدلة |
| `valuation` | التحويل وإعادة التقييم |

مجلد `internal/kernal` الجذر ليس حزمة مجال إضافية ضمن جدول المسؤوليات. ملفات الميثاق والفحوص والوثائق الموجودة في الجذر توثق أو تتحقق من حدود الحزم؛ ولا تمنح الجذر ملكية مفاهيم أو قواعد مجال.

**خارج النطاق صراحةً:** `Public API`، و`SPI`، وطبقة التطبيق، والمحول، وواجهات التخزين، وتنفيذ المعاملات والأقفال في البنية التحتية، والنقل، والمصادقة والتفويض، والأنظمة القطاعية أو المجالات المحاسبية التي ليست حزمة من الحزم التسع أعلاه.

**تنبيه:** الجدول يحدد نطاق الوثيقة ومواضع المسؤولية المعمارية، ولا يعني اكتمال التنفيذ أو نجاح الاختبارات. إثبات التنفيذ مكانه تقارير التحقق والاختبارات.

## 4. الهدف المعماري

أن تكون لكل واحدة من الحزم التسع داخل `internal/kernal` حدود واضحة ومفهومة، ومالك واحد لكل مفهوم وقاعدة مجال، ومصدر حقيقة واحد، وعقود معلومة للتفاعل مع الحزم الأخرى، مع منع تسرب منطق المجال إلى تفاصيل التخزين أو النقل.

النتائج المطلوبة:

- مصدر حقيقة واحد لكل مفهوم.
- مالك واحد لكل invariant.
- فصل تعريف القيد عن التحقق والترحيل.
- فصل البيانات المرجعية عن قرار السماح السياسي.
- عدم قابلية تعديل الحقائق المالية المرحلة في مكانها.
- قابلية إعادة بناء الأرصدة والإسقاطات من القيود المرحلة.
- إبقاء الحزم الداخلية مستقلة عن SQL والشبكة والنقل والمزودين الخارجيين.
- إمكانية اختبار كل حزمة واختبار عقود التفاعل بين الحزم التسع.
- عدم تحويل هذه الوثيقة إلى تعريف مسؤوليات الطبقات أو المكونات الواقعة خارج `internal/kernal`.

لا يعني الهدف إنشاء حزمة لكل مفهوم صغير، أو تحويل الحزم إلى خدمات مستقلة، أو منع التعاون بينها، أو نقل كل قواعد العمل إلى Aggregate واحد.

## 5. النموذج الإلزامي لوصف المسؤولية

يجب أن تتضمن وثيقة أي مسؤولية الحقول التالية:

| الحقل | المقصود |
| --- | --- |
| الحالة الحالية | موضع المسؤولية المعماري ومدى اعتمادها |
| بيان المسؤولية | لماذا توجد، وما النتيجة التي تملكها |
| الهدف | النتيجة التي يجب أن تحققها |
| النطاق الداخل | المفاهيم والقرارات والقواعد التي تملكها |
| خارج النطاق | ما لا تملكه ولا تنفذه |
| قواعد المجال | القواعد التي تفرضها |
| المدخلات | الحقائق والقرارات التي تحتاج إليها |
| المخرجات | النتائج أو القرارات التي تقدمها |
| حدود التعاون | الجهات التي تتفاعل معها وطبيعة العلاقة |
| مصدر الحقيقة | حقيقة أصلية أم إسقاط أم قرار مشتق |
| ضوابط التغيير | ما يستلزم ADR أو ترحيلاً توافقياً |
| دليل الالتزام | الاختبارات والعقود والفحوص التي تثبت الحدود |

# 6. تعريف المسؤوليات

## 6.1 القيم المالية والأنواع الأساسية — `types`

**الحالة:** مسؤولية تأسيسية معتمدة.

**المسؤولية:** ضمان تمثيل المال والعملات والمعرفات والقواعد العددية الأساسية بدقة وحتمية.

**الهدف:** توفير أساس موحد يمنع فقد الدقة أو اختلاط العملات أو اختلاف سلوك العمليات المالية.

**داخل النطاق:**

- تمثيل المال والقيم العشرية والعملات.
- خصائص العملة ووحدتها الصغرى.
- المعرفات والأنواع الأساسية المشتركة (`CompanyID`، `AccountID`، `JournalID`، `FiscalPeriodID`، إلخ).
- قواعد التقريب الحسابي الأساسية.
- التحقق من صلاحية القيمة من منظور تمثيلها.
- أخطاء sentinel الأساسية المتعلقة بالتمثيل المالي والعملات (`ErrCurrencyMismatch`، `ErrInvalidCurrency`، `ErrInvalidAmount`، `ErrAmountExceedsPrecision`، `ErrSubMinorUnitAmount`، `ErrNegativeAmountProhibited`).

> **ملاحظة حالة حالية — أخطاء مجال مستضافة مؤقتاً:** يحتوي `types/errors.go` حالياً على أخطاء sentinel تخص مجالات أخرى (مثل `ErrFiscalPeriodClosed`، `ErrCannotPostToParentAccount`، `ErrAccountNotFound`، `ErrUnbalancedMove`، `ErrMoveAlreadyPosted`، `ErrCannotModifyPostedMove`). هذه الأخطاء مستضافة مؤقتاً ومُعاد تصديرها (alias) في الحزم المالكة لها (`masterdata`، `posting`، `journal`). يجب نقلها إلى الحزم المالكة ضمن خطة إصلاح حدود المسؤوليات؛ راجع `docs/plans/KERNEL_DDD_BOUNDARY_REMEDIATION_PLAN.md`.

**خارج النطاق:**

- توازن القيد المحاسبي.
- أهلية الحساب أو الفترة للترحيل.
- اختيار سياسة العملة.
- التحويل المحاسبي وإعادة التقييم.
- جلب أسعار الصرف أو التخزين أو التقارير.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. يمنع استخدام الأعداد الثنائية العائمة في الحسابات المالية.
2. تكون عمليات المال محددة الدقة وقابلة للتكرار.
3. لا تختلط العملات في العمليات التي تتطلب عملة واحدة.
4. القيم الأساسية غير قابلة للتغيير بعد إنشائها.
5. التقريب صريح ومحدد ولا تسقط فروقه بصمت.
6. لا تعيد الحزم الأخرى تعريف تمثيل المال أو التقريب الأساسي.

**التعاون:** تستخدمها جميع المسؤوليات؛ `valuation` للحسابات المالية و`posting` للتحقق والتقريب في سياق الترحيل.

**مصدر الحقيقة:** القيم والتمثيل العددي، لا القرارات المحاسبية المركبة.

## 6.2 الأخطاء المرمّزة للتوافق — `apperrors`

**الحالة:** مسؤولية توافق معزولة عن حزم النواة الثمان الأخرى؛ تُستهلك من طبقة SDK (`pkg/sdk`) لتصنيف الأخطاء وتحويلها إلى أخطاء SDK عامة، لكنها ليست حالياً طبقة أخطاء مركزية تعتمد عليها بقية حزم النواة.

**المسؤولية:** توفير شكل مستقر للأخطاء المرمّزة التي يحتاج إليها المستهلك للتعرف الآلي على نوع الخطأ.

**الهدف:** حماية التوافق دون فرض اعتماد مركزي على هذه الحزمة داخل كل مسؤوليات المجال.

**داخل النطاق:** رمز الخطأ، الرسالة، السبب الاختياري، وفحص الرمز عبر أغلفة الأخطاء.

**خارج النطاق:** تحديد قواعد المجال، أو تقرير قبول القيد، أو امتلاك أخطاء كل مجال، أو إدارة التنبيهات والسجلات التشغيلية.

**قواعد التوافق:**

1. لا يتغير معنى رمز منشور بصمت.
2. لا يعاد استخدام رمز لمعنى مختلف.
3. أي تغيير مؤثر في التوافق يوثق بقرار وترحيل.
4. الحزمة المالكة للقاعدة هي التي تكتشف المخالفة وتقرر الرفض.

**مصدر الحقيقة:** شكل الخطأ المرمّز فقط، لا دلالة المجال التي أدت إليه.

## 6.3 القيد المحاسبي ودورة حياته — `journal`

**الحالة:** مسؤولية مجال مستقلة ومعتمدة.

**المسؤولية:** امتلاك التعريف القانوني للقيد وأسطره وبيانات حالته وروابط العكس والتصحيح، مع إبقاء تنفيذ انتقالات الحالة ضمن مسار الترحيل.

**الهدف:** توفير نموذج قيد مستقل عن طريقة إنشائه أو ترحيله أو تخزينه.

**داخل النطاق:**

- هوية القيد وبياناته وأسطره.
- تمثيل حالة القيد وبيانات دورة حياته وروابط العكس والتصحيح.
- ثوابت بنية القيد.
- بيانات وروابط العكس والتصحيح.
- منع العبث بالحقيقة المرحلة في مكانها.

**خارج النطاق:**

- التحقق المركزي من توازن المدين والدائن.
- أهلية الحساب أو العملة أو الفترة.
- حل السياسات النافذة.
- تنسيق الترحيل أو تنفيذ التخزين.
- احتساب الأرصدة أو إسقاطات دفتر الأستاذ.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. لا يصبح القيد حقيقة مالية مرحلة إلا بعد اجتياز مسار الترحيل.
2. لا يجوز تعديل أو حذف القيد المرحّل في مكانه.
3. التصحيح يتم بقيد مستقل عكسي أو تصحيحي مرتبط بالأصل.
4. لا تملك هذه المسؤولية تنفيذ انتقال الحالة أو اعتماد الترحيل؛ ينسق `posting` انتقالات الحالة ضمن المسار المركزي وفق قواعد المجال.
5. علاقة القيد العكسي بالأصل واضحة وقابلة للتحقق.
6. أسطر القيد تظل ضمن دورة حياة Aggregate القيد.
7. امتلاك نموذج القيد لا يمنح هذه المسؤولية ملكية انتقال الحالة أو الترحيل أو التخزين.

**التعاون:** يستهلكه `posting` للتحقق والترحيل، و`policy` للسياق، و`ledger` للإسقاطات، و`valuation` لتوليد قيود التقييم.

**مصدر الحقيقة:** القيد المرحّل وأسطره هي مصدر الحقيقة للأثر المحاسبي.

## 6.4 البيانات المرجعية المحاسبية — `masterdata`

**الحالة:** المصدر المرجعي المعتمد.

**المسؤولية:** امتلاك بيانات الشركة والحسابات واليوميات والتقويم والأبعاد وخصائصها وصلاحيتها الزمنية.

**الهدف:** ضمان استخدام عمليات المحاسبة لبيانات مرجعية صحيحة ومتسقة ومقيدة بالشركة والتاريخ.

**داخل النطاق:**

- الشركة ونطاقها.
- دليل الحسابات والحسابات وشجرتها.
- خصائص الحساب وصلاحيته الزمنية.
- اليوميات ونطاقها.
- السنوات والفترات المالية وحالاتها.
- الفترات الخاصة والتسويات والتدقيق.
- مراكز التكلفة والأبعاد التحليلية.
- عقود قراءة البيانات المرجعية.

**خارج النطاق:**

- التخزين الملموس.
- قرار سياسة الترحيل أو العملة.
- إنشاء القيود أو ترحيلها أو عكسها.
- احتساب الأرصدة.
- التقارير.
- المستخدمون والمصادقة والصلاحيات.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. كل كيان مرجعي تابع لشركة يحترم نطاقها.
2. يرفض غياب أو عدم صحة نطاق الشركة حيث يكون إلزامياً.
3. علاقات الحسابات الهرمية متسقة ضمن الشركة.
4. لا يستخدم الحساب خارج فترة صلاحيته.
5. صلاحية الحساب والفترة تحدد بالنسبة إلى تاريخ العملية.
6. لا يرحل مباشرة إلى حساب تجميعي.
7. لا يتجاوز الإغلاق الصلب للفترة أو السنة.
8. لا تعامل الفترات الخاصة كفترات عادية يحددها التاريخ وحده.
9. تبقى بيانات الحساب والفترة المرجع الوحيد ولو وجدت نماذج عرض مقابلة.

**التعاون:** يقدم الحقائق إلى `policy` و`posting`؛ ولا يعتمد على نماذج `ledger` كمصدر مرجعي بديل.

**مصدر الحقيقة:** البيانات المرجعية المحاسبية.

## 6.5 السياسات والأهلية — `policy`

**الحالة:** مسؤولية سياسات مؤرخة ومقيدة بالشركة.

**المسؤولية:** تحديد القواعد السياسية النافذة التي تحكم السماح باستخدام البيانات المرجعية في عملية محاسبية معينة.

**الهدف:** فصل القواعد القابلة للإصدار والتغيير عن الحقائق المرجعية وعن عملية الترحيل.

**داخل النطاق:**

- سياسات الترحيل والعملات.
- نسخ السياسات وتواريخ سريانها.
- حل السياسة المناسبة للشركة والتاريخ.
- منع تعارض نوافذ السريان.
- تقييم أهلية الحسابات والأبعاد.
- بصمة السياسة المستخدمة عند الحاجة إلى إثبات تاريخي.

**خارج النطاق:**

- إنشاء الحسابات أو تغييرها.
- امتلاك التقويم المالي أو حالة الإغلاق.
- تنفيذ الترحيل أو التخزين أو الأقفال.
- إدارة المستخدمين أو الموافقات أو RBAC.
- توفير أسعار الصرف الخارجية.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. كل سياسة محددة بنطاق الشركة.
2. اختيار السياسة مرتبط بتاريخ العملية.
3. يرفض التداخل أو الغموض في نوافذ السريان.
4. لا توجد سياسة افتراضية خفية عند غياب سياسة نافذة إذا كان العقد يفرض الفشل المغلق.
5. قرار الأهلية قابل للتفسير وإعادة التحقق.
6. السياسة لا تغير حقيقة الحساب أو الفترة.
7. لا تتجاوز السياسة الإغلاق الصلب أو قاعدة مجال أعلى.
8. تثبت السياسة التي أثرت في القيد التاريخي متى اشترط العقد ذلك.
9. لا يعيد تغيير السياسة لاحقاً تفسير قيد سابق.

**التعاون:** تستهلك حقائق `masterdata` وسياق `journal`، وتقدم القرار إلى `posting`.

**مصدر الحقيقة:** السياسات وقرارات الأهلية، لا البيانات المرجعية نفسها.

## 6.6 التحقق والترحيل والعكس — `posting`

**الحالة:** المسار المركزي المعتمد للترحيل.

**المسؤولية:** تجميع شروط المجال والتحقق من سلامة القيد وإصدار قرار ترحيل حتمي، ثم تفويض التنفيذ الذري للمضيف أو المحول.

**الهدف:** منع تحول أي مسودة إلى حقيقة مرحلة قبل اجتياز شروط الهوية والنطاق والسياسات والفترات والحسابات والعملات والتوازن والتقريب.

**داخل النطاق:**

- ترتيب خطوات التحقق.
- التحقق من الهوية والنطاق والتصنيف والحالة.
- التحقق من اليومية والفترة.
- استهلاك قرارات السياسات والأهلية.
- التحقق من العملات والتوازن.
- تطبيق التقريب في سياق الترحيل.
- بناء بيانات العكس وفق قواعد المجال.
- تجهيز مدخلات التفويض إلى التنفيذ الذري.
- اشتقاق نطاق idempotency والبصمات.
- إنتاج مفاتيح أقفال مرتبة حتمياً دون تنفيذ الأقفال.

**خارج النطاق:**

- تعريف القيد أو امتلاك دورة حياته.
- امتلاك الحسابات والفترات أو تعريف السياسات.
- SQL أو فتح المعاملة أو تنفيذ الأقفال.
- retry أو فرض التفرد في قاعدة البيانات.
- حفظ أرصدة مادية أو إنشاء تقارير.
- النقل والشبكة.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. لا يرحل قيد ناقص أو غير صالح.
2. كل ترحيل يمر بمسار تحقق مركزي.
3. يتحقق من نطاق الشركة قبل القراءة المرجعية الحساسة.
4. يتحقق من نفاذ الحسابات والفترات والسياسات في تاريخ العملية.
5. يتحقق التوازن بالعملة الوظيفية وفق قواعد النواة.
6. لا تسقط فروق التقريب بصمت.
7. العكس لا يعدل القيد الأصلي.
8. إعادة الطلب آمنة وفق عقد idempotency.
9. مفاتيح الأقفال حتمية ومرتبة قبل تسليمها للمضيف.
10. نجاح التحقق وحده لا يعني نجاح الترحيل؛ لا بد من اكتمال الحفظ الذري.
11. لا توجد نتيجة نجاح جزئي عند فشل وحدة العمل.
12. لا يتجاوز التقييم أو التسوية مسار الترحيل.

**التعاون:** يستهلك `journal` و`masterdata` و`policy` و`types`، ويفوض التنفيذ إلى المضيف، ويستقبل قيوداً مرشحة من `valuation`.

**مصدر الحقيقة:** يملك قرار التحقق والترحيل، لا تعريف القيد أو البيانات المرجعية. يصبح القيد حقيقة مرحلة بعد نجاح التنفيذ الذري.

## 6.7 إسقاطات القراءة والنماذج المرجعية — `ledger`

**الحالة:** مسؤولية إسقاطات قراءة وتوافق؛ ليست سجل الأستاذ العام الأصلي ولا مخزن حركة/أرصدة مستقلاً. نماذج `ledger.Account` و`ledger.FiscalPeriod` وما يرتبط بها DTOs توافقية؛ المرجع المعتمد للحسابات والتقويم هو `masterdata`.

**المسؤولية:** تقديم تمثيلات قراءة وتوافق مشتقة من الحقائق المرحلة دون امتلاكها أو إعادة تعريفها.

**الهدف:** توفير أشكال مناسبة للاستهلاك وإعادة بناء النتائج مع إبقاء مصدر الحقيقة في القيود والبيانات المرجعية في مالكها.

**داخل النطاق:**

- نماذج توافق مرجعية خفيفة متصلة بأشكال السطح العام؛ وهي ليست مرجع أهلية أو مصدراً مرجعياً للحسابات والفترات.
- إسقاطات قراءة مشتقة من القيود المرحلة.
- إعادة بناء حتمية للحركات والأرصدة المشتقة.
- تمثيل البيانات للقراءة وفق العقود.

**خارج النطاق:**

- امتلاك الحسابات أو الفترات المرجعية.
- قبول أو رفض الترحيل.
- إنشاء حركة مالية أصلية مستقلة.
- تعديل الأرصدة مباشرة أو تخزين رصيد مادي داخل النواة.
- إدارة السياسات أو تنفيذ التقارير والإفصاحات.
- تعديل القيود المرحلة.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. كل إسقاط مشتق من مصدر حقيقة معروف.
2. إعادة البناء حتمية عند ثبات المدخلات والترتيب.
3. الإسقاط أو الرصيد المشتق ليس مصدراً بديلاً للحقيقة.
4. لا يستخدم نموذج التوافق لاتخاذ قرار أهلية أو ترحيل.
5. يمنع الانحراف الصامت عن النموذج المرجعي المالك.
6. لا يكتسب نموذج القراءة ملكية مستقلة لبيانات الحساب أو الفترة.

**التعاون:** يستهلك القيود المرحلة، ويتعامل مع البيانات المرجعية عند الحاجة للعرض، ويقدم مخرجات للمستهلكين.

**مصدر الحقيقة:** لا يملك حقيقة مالية أصلية؛ مخرجاته مشتقة أو توافقية.

## 6.8 التدقيق وسلامة الأدلة — `governance`

**الحالة:** مسؤولية مستقلة لسلسلة التدقيق والتحقق من سلامتها.

**المسؤولية:** ضمان أثر تدقيقي مترابط وقابل للتحقق للأحداث المحاسبية المهمة واكتشاف العبث أو الحذف أو عدم اتساق السلسلة.

**الهدف:** توفير دليل موثوق على ما حدث وتسلسله وسلامة سجل التدقيق بالنسبة إلى نقاط تحقق مستقلة.

**داخل النطاق:**

- سلسلة التدقيق الإلحاقية.
- الربط التشفيري بين السجلات.
- التحقق من سلامة التسلسل والمحتوى.
- التحقق بالاستناد إلى لقطة متسقة.
- التحقق من نقاط التفتيش الخارجية.
- التمييز بين عدم اتساق قابل لإعادة المحاولة وفشل نزاهة حقيقي.

**خارج النطاق:**

- قرار الترحيل أو توازن القيد.
- تعريف القيد أو امتلاك البيانات المرجعية.
- احتساب الأرصدة.
- التخزين الملموس أو الاتصال بالشبكة.
- المصادقة وإدارة الصلاحيات.
- استبدال الحقيقة المالية بسجل التدقيق.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. سجل التدقيق إلحاقي وفق العقد.
2. الربط بين السجلات قابل للتحقق.
3. صحة بادئة السلسلة لا تثبت عدم حذف ذيلها.
4. تستخدم نقطة تحقق خارجية مستقلة عند اشتراط إثبات اكتمال السلسلة.
5. تستند عملية التحقق إلى لقطة متسقة.
6. لا يحل سجل التدقيق أو بصمته محل القيد.
7. يحفظ الأثر المالي وأثر التدقيق وفق وحدة العمل الذرية المطلوبة.

**التعاون:** يتلقى آثار العمليات من مسار الترحيل والمضيف ويستخدم عقوداً مجردة.

**مصدر الحقيقة:** أدلة التدقيق وسلامة السلسلة فقط، لا القيود أو الأرصدة.

## 6.9 التقييم والتحويل وإعادة التقييم — `valuation`

**الحالة:** مسؤولية مجال للتقييم بالعملات الأجنبية والتحويل وإعادة التقييم.

**المسؤولية:** تطبيق قواعد التقييم على المبالغ والأرصدة باستخدام أسعار صرف وتواريخ وسياسات محددة، وإنتاج أثر محاسبي مرشح للترحيل.

**الهدف:** جعل عمليات التحويل وإعادة التقييم قابلة للتفسير والتكرار، وتحويل فروق التقييم إلى قيود تمر بمسار الترحيل المعتمد.

**داخل النطاق:**

- تمثيل أسعار الصرف ضمن المجال.
- اختيار السعر وفق التاريخ والغرض والقواعد.
- تحويل المبالغ بين العملات.
- إعادة تقييم البنود النقدية.
- تحديد فروق التقييم.
- توليد قيد تقييم مرشح للترحيل.
- منع تكرار أثر العملية وفق عقد idempotency.

**خارج النطاق:**

- جلب الأسعار من الإنترنت أو مزود خارجي.
- إدارة مفاتيح API واتصالات المزود.
- تعريف تمثيل المال والتقريب الأساسي.
- امتلاك القيود المرحلة أو تنفيذ ترحيلها وحفظها.
- إنشاء أرصدة مستقلة أو إعداد القوائم والإفصاحات.
- تقرير سياسة العملة العامة إذا كانت مملوكة للسياسات.

**قواعد المجال التي تملكها المسؤولية (على مستوى الحدود):**

1. سعر الصرف صالح وفق التاريخ والغرض ومصدره المعتمد.
2. اختيار السعر محدد وقابل للتكرار.
3. تستخدم قواعد المال والتقريب المعتمدة.
4. لا تنتج عملية التقييم أثراً مالياً غير متوازن.
5. مدخلات التقييم ونتائجه قابلة للتتبع.
6. يمنع تكرار قيد التقييم عند إعادة الطلب.
7. يمر القيد الناتج عبر `posting`.
8. لا يعدل التقييم قيداً مرحّلاً سابقاً.

**التعاون:** يعتمد التنفيذ الحالي على `types` و`journal` و`masterdata` و`posting`؛ ويستقبل أسعار الصرف عبر عقد مزود مجرد (`RateProviderSPI`) يمرر إليه. الاعتماد على `posting` يشمل استخدام `posting.IdempotencyScope` و`posting.IdempotencyRevaluation` و`posting.ValidateEntryDoubleEntry` و`posting.BuildReversalEntryAt` وأخطاء `posting` مباشرة. لا يعني ذلك أن `valuation` يملك مزود الأسعار أو يملك سياسة العملة العامة.

> **ملاحظة حالة حالية — اقتران مباشر بـ`posting`:** اعتماد `valuation` على أنواع `posting` ودوالها يتجاوز التعاون الدلالي المتوقع (تمرير قيد عبر مسار الترحيل). يجب فحص إمكانية عزل عقود idempotency والتحقق في واجهات مجردة ضمن خطة إصلاح حدود المسؤوليات.

**مصدر الحقيقة:** نتائج التقييم ومدخلات العملية المثبتة، لا مصدر أسعار خارجي ولا القيود المرحلة.

## 6.10 حدّ مجلد `internal/kernal` الجذر

لا يُعامل مجلد `internal/kernal` الجذر بوصفه حزمة مجال أو مسؤولية محاسبية مستقلة. دوره في نطاق هذه الوثيقة هو احتواء الحزم التسع والوثائق أو الفحوص التي قد تثبت حدودها.

- لا يملك الجذر مفهوماً محاسبياً لمجرد وجود ملف فيه.
- لا تنقل مسؤولية أي حزمة إلى الجذر لأغراض التنظيم أو التوثيق.
- لا تُدرج وثائق الميثاق أو التقارير أو مصفوفات التتبع ضمن جدول حزم المجال.
- أي قاعدة اعتماد أو فحص معماري على مستوى الجذر تُوثق في ميثاق/مواصفة معمارية منفصلة، ويُشار إليها هنا فقط عند تأثيرها في حدود الحزم.

# 7. الحدود بين المسؤوليات المتداخلة

| موضوع التداخل | المالك | ما تفعله المسؤوليات الأخرى |
| --- | --- | --- |
| تعريف القيد وبيانات حالته | `journal` | `posting` يتحقق وينسق انتقال الحالة والترحيل |
| توازن القيد وقبول الترحيل | `posting` | `journal` يوفر نموذج القيد؛ `types` يوفر الحسابات الدقيقة |
| الحساب والفترة والشركة | `masterdata` | `policy` يقيّم الأهلية؛ `posting` يستهلك الحقائق |
| السياسة وأهلية الاستخدام | `policy` | `masterdata` يوفر الحقائق؛ `posting` يستهلك القرار |
| الحقيقة المالية | القيود المرحلة في `journal` | `ledger` يشتق إسقاطات |
| تمثيل المال والتقريب الأساسي | `types` | `valuation` و`posting` يطبقانها في سياقهما |
| التحويل وإعادة التقييم | `valuation` | `posting` يرحل القيد الناتج |
| سلامة سجل التدقيق والأدلة | `governance` | تتعاون الحزم المعنية بتقديم الأدلة؛ لا تملك الحزم الأخرى تعريف سلامة السجل |
| إنشاء قيد التقييم | `journal` يملك نموذج القيد | `valuation` يحسب أثر التقييم ويطلب إنشاء قيد وفق عقد `journal`، ثم يمر الناتج عبر `posting` |
| إسقاطات القراءة وإعادة بنائها | `ledger` يملك معنى الإسقاط ومصدره | الحزم الأخرى لا تعدّل الإسقاط مباشرة؛ التنفيذ المادي خارج نطاق هذه الوثيقة |
| تنفيذ المعاملة والأقفال | خارج الحزم التسع | `posting` يحدد متطلبات التنفيذ/التنسيق التي يحتاجها عقده دون امتلاك التنفيذ التقني |

### 7.1 قواعد الفصل الحاسمة

- `journal` يملك نموذج حالة القيد وقواعد انتقاله الدلالية وحمايات عدم التغيير؛ لكنه لا ينسق مسار الترحيل ولا ينفذ الحفظ. `posting` هو المسار المركزي الذي يتحقق ويختم حالة الترحيل ويفوض الحفظ الذري.
- `posting` لا يملك تعريف القيد أو البيانات المرجعية أو السياسات.
- `masterdata` لا يقرر السياسة العامة.
- `policy` لا يغير حقيقة الحساب أو الفترة.
- `ledger` لا يصبح مصدراً مالياً مستقلاً.
- `types` لا ينفذ المعالجة المحاسبية عالية المستوى.
- `valuation` لا ينشئ مسار ترحيل بديلاً، ولا يتجاوز `journal` عند إنشاء القيد.
- `governance` لا يحل محل الحقيقة المالية.
- `ledger` يملك قواعد الإسقاط وإعادة بنائه من القيود المرحلة، لكنه لا يملك حقيقة مالية بديلة.
- لا تحدد هذه الوثيقة كيفية تنفيذ المضيف/المحول للتخزين الفعلي؛ تكتفي بتحديد متطلبات العقد التي تحتاجها حزم `kernal`.

# 8. قواعد الملكية والحدود العامة للنواة

تسري الضوابط التالية على جميع المسؤوليات. وهي قواعد حاكمة للملكية والحدود وليست بديلاً عن مواصفات المجال أو الجودة أو التشغيل؛ لا تحدد هنا الخوارزميات أو حالات الاختبار أو آليات التنفيذ.

## 8.1 الملكية ومصدر الحقيقة

1. لكل مفهوم مجال مالك حزمة واحدة مسؤولة عن تعريف معناه وحدوده ومصدر حقيقته.
2. لكل invariant مالك مجال واحد مسؤول عن تعريف معناها وشروط صحتها.
3. يجوز توزيع آليات فرض الـinvariant والتحقق منه بين الحزمة المالكة والحزم المتعاونة، دون نقل ملكيته أو إعادة تعريفه.
4. يجوز الاستهلاك ولا تجوز إعادة التعريف.
5. لا تنشأ نسخة ثانية من مصدر الحقيقة لأجل سهولة القراءة أو التوافق.
6. نموذج العرض أو التوافق يجب أن يعلن أنه مشتق، وأن يملك قواعد تحويل صريحة.

## 8.2 النطاق والهوية

1. السياق الأعلى الذي يستدعي عملية النواة هو المسؤول عن توفير `CompanyID` ضمن سياق موثوق ومصرح به؛ هذا السياق خارج نطاق الحزم التسع.
2. تتحقق الحزم التي تحتاج نطاق الشركة من وجود `CompanyID` وصلاحيته واتساقه مع مدخلات العملية.
3. لا تستنتج حزم `kernal` نطاق الشركة من هوية المستخدم أو من قيمة غير موثوقة، ولا تمنح صلاحية وصول.
4. لا تخلط بيانات شركتين في عملية واحدة دون عقد صريح.

## 8.3 الزمن والنفاذ

1. تقيم البيانات والسياسات وفق تاريخ العملية.
2. لا تستخدم ساعة النظام مباشرة في قرار مجال غير مضبوط.
3. اختيار النسخة الزمنية حتمي.
4. لا يعيد تغيير لاحق تفسير حقيقة مالية سابقة.
5. توثق حدود نوافذ السريان والتداخل والفجوات.

## 8.4 سلامة القيد

1. لا يصبح القيد حقيقة مرحلة إلا بعد اجتياز الترحيل.
2. يتحقق التوازن بالعملة الوظيفية وفق قواعد النواة.
3. يمنع تعديل أو حذف الحقيقة المرحلة في مكانها.
4. التصحيح بعكس أو قيد تصحيحي مرتبط.
5. لا يعدل الرصيد مباشرة؛ هو نتيجة مشتقة.
6. إعادة بناء الرصيد حتمية ومقيدة بالشركة والعملات.

## 8.5 الدقة المالية

1. يمنع استخدام الأعداد الثنائية العائمة في الحسابات المالية.
2. الدقة وأسعار الصرف والتقريب محددة.
3. لا تسقط فروق التقريب بصمت.
4. تعالج فروق التقريب وفق القواعد المعتمدة.
5. لا تختلف قواعد التقريب بين مسارين ينتجان الأثر المالي نفسه.

## 8.6 السياسات

1. كل سياسة محددة بالنطاق والإصدار وتاريخ السريان.
2. يرفض تعارض النسخ أو غياب النسخة النافذة وفق قاعدة الفشل المغلق.
3. تثبت السياسة التي أثرت في القيد التاريخي.
4. لا يغير تحديث السياسة معنى قيد سابق.

## 8.7 التدقيق والنزاهة

1. آثار العمليات المالية المهمة قابلة للتتبع.
2. `governance` يملك قواعد سلامة سلسلة التدقيق والتحقق من الأدلة التي تقع ضمن مسؤوليته.
3. يجب أن يحدد عقد نقطة التحقق/الـcheckpoint: الجهة التي تنشئه، والجهة التي تعتمد أو تتحقق منه، ونطاق الإثبات، وكيفية التعامل مع فقده أو عدم اكتماله. لا تفترض هذه الوثيقة أن كل هذه الأدوار داخل `kernal`؛ تُسند داخل الحزم فقط الوظائف التي تؤكدها مواصفة المجال المعتمدة.
4. التحقق من اكتمال السلسلة أقوى من التحقق من بادئة صحيحة.
5. لا يحل سجل التدقيق محل الحقيقة المالية.
6. لا تحدد هذه الوثيقة طريقة التخزين أو الضمان الذري خارج الحزم؛ تحدد الحزم متطلبات العقد اللازمة لصون الأثر.

## 8.8 الحتمية وIdempotency

1. المدخلات المثبتة والسياق الزمني والسياسات نفسها تنتج النتيجة نفسها.
2. إعادة الطلب لا تنتج أثراً مالياً مكرراً.
3. نطاق idempotency وبصمة الطلب محددان.
4. المجال يشتق الهوية الدلالية للعملية؛ والمحول يفرض التفرد والتنفيذ الذري وفق العقد.
5. لا يعلن النجاح قبل اكتمال الحفظ الذري.

## 8.9 استقلال النواة

1. لا SQL أو محرك قاعدة بيانات داخل النواة.
2. لا HTTP أو gRPC أو بروتوكول نقل داخل النواة.
3. لا اتصال بمزودي أسعار أو خدمات خارجية.
4. لا إدارة لمستخدمي النظام أو كلمات المرور أو جلسات المصادقة.
5. لا مفاهيم قطاعية تشغيلية بوصفها مفاهيم أصلية للنواة.
6. تحول الأنظمة القطاعية أحداثها إلى أثر مالي مجرد خارج النواة.

# 9. عقود التفاعل بين المسؤوليات

يجب أن يحدد كل تفاعل **بين الحزم التسع داخل `internal/kernal`**:

- الحزمة المالكة للبيانات أو القرار.
- الحزمة المستهلكة.
- سبب التفاعل.
- الحد الأدنى من البيانات/القرار الذي ينتقل.
- هل البيانات آنية أم نسخة مؤرخة أو مجمدة.
- سلوك الفشل عند الغياب أو التعارض.
- متطلبات الاتساق والذرية.
- كيفية التتبع وإعادة التحقق.
- قواعد التوافق عند تغيير العقد.

**قواعد إلزامية:**

1. المستهلك لا يعدل بيانات المنتج.
2. لا يخمن المستهلك بيانات مفقودة ولا يستبدلها بقيمة افتراضية غير معتمدة.
3. الفشل واضح ومصنف.
4. العقد لا يكشف تفاصيل تنفيذية لا يحتاجها المستهلك.
5. لا تتسرب نماذج التخزين أو النقل إلى نموذج المجال.
6. تثبت القرارات التاريخية التي أثرت في أثر مالي.

# 10. تغيير المسؤوليات والحدود

أي تغيير في مسؤولية أو نطاق أو قاعدة مجال داخل إحدى الحزم التسع يتطلب:

1. تحديد المالك الحالي للمفهوم والقاعدة.
2. وصف المشكلة التي لا يمكن حلها ضمن الحدود الحالية.
3. بيان سبب عدم كفاية تعديل محلي.
4. تحديد الحدود الجديدة والمالك الجديد إن وجد.
5. تحليل الأثر على مصدر الحقيقة والعقود والمستهلكين.
6. التحقق من اتجاه الاعتماد وعدم إنشاء دورة.
7. تحليل أثر التغيير على القيود التاريخية والتوافق العام.
8. إضافة اختبارات تثبت الملكية وعدم الازدواج.
9. تحديث هذه الوثيقة وخريطة المعمارية وسجل ADR.
10. رفض التغيير إذا بقيت قاعدة بلا مالك أو أصبح لها أكثر من مالك.

## 10.1 شروط إنشاء مسؤولية جديدة

لا تنشأ مسؤولية جديدة إلا إذا كان لها غرض مجال مستقل، وقواعد مميزة، وحدود قابلة للاختبار، وعقد تفاعل واضح، ولا تنشئ مصدراً ثانياً للحقيقة أو تعقيداً غير مبرر.

## 10.2 مؤشرات مراجعة الحدود

تراجع الحدود إذا تكررت القاعدة في أكثر من مكان، أو لم تملك الحزمة مفهوماً واضحاً، أو اضطر المستهلك إلى إعادة تنفيذ قاعدة المنتج، أو أصبح هناك نموذجان متنافسان للحقيقة.

# 10.3 الفصل بين وثائق المشروع

لا تتحول هذه الوثيقة إلى قائمة أعمال أو مواصفة تفصيلية. يظل توزيع المسؤولية بين الوثائق كما يلي:

1. **هذه الوثيقة:** تحدد مالك المفهوم والقاعدة والعقد، وحدود ما يملكه وما لا يملكه، والعلاقات بين المالكين.
2. **مواصفات المجال:** تفصل معنى المفاهيم وقواعد المجال وشروط الصحة والحالات الحدية ومدخلات القاعدة ومخرجاتها.
3. **مواصفات الجودة:** تحدد معايير الجودة وبوابات القبول وطرق التحقق والاختبارات والأدلة اللازمة لإثبات الالتزام.
4. **مواصفات التشغيل والتنفيذ:** تحدد آليات التخزين والمعاملات والأقفال والتزامن وإعادة المحاولة والمراقبة والتشغيل، كلٌ ضمن نطاقه.
5. **الخريطة المعمارية:** تصف الحزم والتبعيات والتدفقات الفعلية كما هي في المشروع؛ ولا تنقل ملكية المفاهيم من الحزم المالكة.
6. **سجل ADR:** يسجل القرار المعماري وبدائله وأسبابه وتبعاته؛ ولا تستبدل هذه الوثيقة قراراً معتمداً.

إذا كشفت مراجعة المشروع عن اختلاف بين الحد الموثق والتنفيذ أو بين هذه الوثيقة ومواصفة تفصيلية، يسجل الاختلاف بوصفه تعارضاً أو فجوة إثبات، ولا يعالج بتغيير صامت لملكية المفهوم أو بإضافة تفاصيل تنفيذية إلى هذه الوثيقة.

# 11. معايير قبول الوثيقة والحدود

- [ ] لكل حزمة بيان وهدف واضحان.
- [ ] لكل مسؤولية نطاق داخل وخارج صريح.
- [ ] لكل مسؤولية قواعد قابلة للفحص.
- [ ] لكل مفهوم مصدر حقيقة محدد.
- [ ] العلاقات والتفاعلات موثقة.
- [ ] لا توجد قاعدة بلا مالك أو بمالكين متنافسين.
- [ ] لا تتعارض الحدود مع ADR المعتمد.
- [ ] فصلت الحالة الحالية عن الهدف وعن إثبات التنفيذ.

# 12. علاقتها بالوثائق الأخرى

| الوثيقة | وظيفتها | علاقتها بهذه الوثيقة |
| --- | --- | --- |
| ميثاق المبادئ المعمارية | المبادئ العليا واستقلال النواة | هذه الوثيقة تحولها إلى حدود مسؤوليات |
| خريطة النواة | الحزم والاعتمادات والتدفق الفعلي | هذه الوثيقة تصف معنى الحدود لا تفاصيل الاستيراد |
| سجل ADR | القرارات والبدائل والتبعات | هذه الوثيقة تلخص الحدود ولا تستبدل القرار |
| مواصفات المجال | تفاصيل قواعد المجال | هذه الوثيقة تحدد المالك؛ المواصفة تفصل القواعد |
| عقود SPI/Storage | التفاعل مع المضيف والمحول | خارج النطاق؛ يُشار إليها فقط لتوضيح ما تحتاجه حزم `kernal` من عقد |
| معيار جودة النواة | البوابات والأدلة | يثبت الالتزام بالحدود |
| خطة التنفيذ | المهام والتسلسل والقبول المرحلي | لا تحل محل هذه الوثيقة |

**قاعدة الأولوية:** لا تستبدل هذه الوثيقة ADR مقبولاً أو مواصفة مجال تفصيلية. عند التعارض يسجل التعارض ويحسم بقرار صريح، ثم تحدث الوثائق المتأثرة.
